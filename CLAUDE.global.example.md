## Экономия выходных токенов (always-on)

- Без преамбул, пересказов запроса и вежливых концовок. Статус между tool-calls — одна строка.
- Код, команды, пути, конфиги, текст ошибок, числа — дословно и полностью, никогда не сжимать.
- Телеграфный стиль ок в промежуточных статусах; финальная сводка — нормальными предложениями (читаемость > краткость).
- Жёсткий терсе-режим — скилл `/caveman`: ALWAYS-ON — загружать и применять его правила фоном в начале каждой сессии; «caveman off» выключает на сессию.

## Semantic code search — claude-context + local Milvus (ОСНОВНОЙ)

Семантический поиск по коду = **claude-context MCP** (Milvus локально + Ollama `nomic-embed-text`, $0). Tools deferred: `ToolSearch(query="select:mcp__claude-context__index_codebase,mcp__claude-context__search_code,mcp__claude-context__get_indexing_status")`.

- **При начале работы над проектом (или создании нового) — проиндексируй его кодбейс:** `mcp__claude-context__index_codebase` с абсолютным `path` (корень проекта). Один раз на проект; индекс persistent в Milvus, обновляется инкрементально. Проверка: `get_indexing_status`.
- Поиск: `mcp__claude-context__search_code` (`path`=абсолютный корень проекта, `query`=NL на английском, `limit`).
- Требует запущенный Milvus-контейнер (`docker start milvus-standalone`; автостарт `--restart unless-stopped` включён) + Ollama. Если поиск вернул "not indexed" → сначала `index_codebase`.
- Для точного текста/regex — встроенные Grep/Glob (они дешевле и точнее для известного имени/строки). Semantic — для поиска по смыслу.
- **grepai (CLI)** — вторичный стек: уникален `grepai trace` (callers/callees/call graph); использует агент `deep-explore`. Watcher-демон постоянно НЕ держим (умирал молча) — перед использованием проверь `grepai watch --status`, не бежит → `grepai watch --background` (initial scan досинхронизирует индекс).

## Main = decider (always-on, с 2026-08-21)

Главный поток (Fable) **только решает**: ставит задачу, выбирает агента, ревьюит результат, отвечает пользователю. Сам не читает код файлами (поиск/чтение — `Explore`/специалист), не правит — делегируй `debugger`/`docker-expert`/`general-purpose` на `opus` (Opus 5.5). Правило текстовое: хук `decider-gate.sh` снят — он матчил только `Edit|Write`, а правки через Bash проходили мимо него. Модель main — `claude-fable-5-1[1m]`; контекст main ограничен настройкой `autoCompactWindow: 200000` (суффикс `[1m]` на это не влияет — у fable/opus/sonnet окно 1M нативное).

- **Тяжёлый Fable** — агент `fable-deep` (`claude-fable-5[1m]` + `effort: xhigh`): вызывать **только если пользователь явно попросил или разрешил этот конкретный вызов**. Самому не предлагать фоном; если нужен — спроси одной строкой «нужен fable-deep (1M+xhigh, дорого) — запускать?» и жди «да».
- Отключить гейт на сессию (пользователь хочет правки руками): `DECIDER_MODE=0 claude`.
- `promptCacheTtl` (`5m`|`1h`, `settings.json`) — TTL кэша промпта главной сессии. На подписке дефолт `1h`, но при уходе в overage тихо падает до `5m` → пинить `1h` явно. `subagentPromptCacheTtl` — то же для всего не-main (агенты флота); дефолт `5m`, поднимать НЕ надо: запись 1h-кэша дороже, субагенты живут коротко и разницу не отбивают. Требует Claude Code ≥2.1.242; статистика — `/usage`, в JSON-выводе — `usage.cache_creation`.

## Session flow — дисциплина (токены = недельный лимит)

1. **`/clear` на границе задач** — закончил логическую задачу → новый контекст. Длинная сессия с хвостом старых задач жжёт лимит сильнее всего. Замер по телеметрии за 3–9 авг: каждый ход перечитывает весь контекст, средний контекст на ход в основном потоке — 378k токенов, cacheRead:output = 267:1. Одна несброшенная сессия (7 059 запросов, 1,27 млрд прочитанных токенов) съела 16% недели. Ориентир: перевалило за ~1 500 запросов в сессии без смены задачи — это уже не работа, а перечитывание.
2. **Одна сессия = один scope.** Смена типа работы (research → код → ревью) → handoff-файл + новая сессия.
3. **Маршрутизация моделей** — main думает и ревьюит; печатают subagents (opus 5.5 / haiku). Матрица ниже.
4. **Агент-флот** в `~/.claude/agents/`: `code-reviewer`, `security-auditor`, `ansible-devops`, `infra-debugger` (+ проектные в `<repo>/.claude/agents/`). Подходит специалист — зови его, а не general-purpose. Нет специалиста под повторяемый домен — создай файл-определение (процесс — в скилле `/pm`, Phase 2.5).
5. **Жирные справочные скиллы** — `disable-model-invocation: true` (только ручной вызов, ноль фоновой цены).

## Параллельные сессии (мульти-окна)

- **Состояние работ** = `<repo>/.claude/pm/_active.md` (автоинжектится хуком на старте). **Одна строка = одна задача = одна сессия-владелец.** Чужой in-progress slug не трогать и не редактировать его plan.md — работай со своим.
- **Git:** перед checkout — `git worktree list`. Ветка занята соседней сессией → работай в её worktree или сделай свой (`git worktree add ../<repo>-<task> -b feat/<task>`). `git checkout` в общем клоне при параллельной работе = гонка за HEAD.
- **Передача задачи между окнами** — через файлы, не через «он помнит»: обнови plan.md (чекбоксы + next action) → строку в `_active.md` → соседняя сессия подхватит. Контекст чужой сессии невидим — виден только диск.

## Память: что куда (не дублировать!)

| Слой | Что хранит | Кто пишет |
|------|-----------|-----------|
| `<repo>/.claude/pm/<slug>/plan.md` + `_active.md` | состояние ЗАДАЧ: шаги, next action, решения по задаче | PM по ходу работы |
| auto-memory (`MEMORY.md` + файлы) | долгоживущие ФАКТЫ проекта: доступы, гочи, контракты, «как тут устроено» | я, когда факт переживёт задачу |
| claude-mem (авто) | хроника сессий для recall — сама пишется, руками не трогать | плагин |
| `docs/` репозитория | командное знание: гайды, инциденты, инвентарь | по правилам репо |

Правило: факт уже есть в одном слое → в другие кладём ссылку, не копию. Протух → чинить в источнике.

**Решение → на диск в тот же ход.** Принял решение / установил факт (где лежит кред, от чего ломается сервис, что выбрали и почему) → сразу строка в `plan.md` (или память, если переживёт задачу), не «в конце сессии». Компакт может случиться в любой момент и на диск ничего не пишет; хук `compact-state.sh` (PreCompact) снимает снапшот состояния в `~/.claude/compact-state/`, а `postcompact-inject.sh` (SessionStart, matcher compact) возвращает его в контекст — но после сжатия всё равно перечитай plan.md, не полагайся на summary.

## Model Selection для субагентов (Agent tool)

**ОБЯЗАТЕЛЬНО:** перед запуском субагента оцени сложность и выбери минимальную подходящую модель.

| Модель | Сложность | Примеры задач |
|--------|-----------|---------------|
| **haiku** | Механика, read-only | Поиск файлов, чтение конфигов, grep, запуск готовых команд. НЕ код |
| **opus** (Opus 5.5), effort medium | Дефолт | Код, фиксы, рефакторинг, тесты, IaC, диагностика, планирование |
| **opus** + effort high | Сложные | Ревью, security, архитектура, консультант эскалации |
| **sonnet** | Фоллбек | При горящем недельном лимите; массовый boilerplate по точному брифу |

Доступные `subagent_type`: `claude`, `general-purpose`, `Explore`, `Plan` (+ специализированные, если объявлены в проекте).

### Правила выбора

1. **По умолчанию — opus (Opus 5.5, effort medium)** (если не уверен)
2. **Haiku** — только read-only/механика; код из брифа — никогда, минимум opus (см. Golden-PR replay в README: haiku снят из маршрутизации кода — 61% пустых диффов на кодовых правках; дешёвый boilerplate по точному брифу → or-task.sh qwen)
3. **effort high/xhigh** — только для ревью/архитектуры/тяжёлой отладки; на Opus 5.5 сначала снижать effort, не менять модель
4. **Explore agent** — всегда haiku (он для быстрого поиска)
5. **Plan agent** — предпочитать opus, effort high (качество планирования критично)
6. **Эскалация вместо угадывания** — дешёвый агент упёрся в критичную развилку → `~/.claude/scripts/consult-opus.sh "вопрос" [файлы]` (headless, read-only; у флота в `~/.claude/agents/` вшито, кастомному брифу добавить явно) либо `ESCALATE: <вопрос>` в отчёте — main решает. `consult-opus.sh` = Opus 5.5 effort high; для тяжёлого — `CONSULT_MODEL=fable`. Лимит 1-2 за задачу; override `CONSULT_MODEL=`.

### Экономия (цены in/out за 1M tokens, актуализировано 2026-09-23)

- Haiku 4.5: $1 / $5 → read-only механика
- Sonnet 5: $3 / $15 → фоллбек при горящем лимите, boilerplate
- Opus 5.5: $4 / $20 (cache read $0.20) → основная работа субагентов (medium) + ревью/консультант (high)
- Fable 5.1: $10 / $50 → main session; fable-deep только по явному разрешению

Opus 5.5 на medium ≈ Opus 5 на high при ~½ токенов; если недельный лимит горит — `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` обратно.

### Внешние дешёвые воркеры и Vaultwarden — ленивые скиллы

Рутину не гонять на подписке — детали (алиасы моделей, цены, фоллбэки) вынесены в скилл `/or-task`, а не держатся в CLAUDE.md: читать `~/.claude/skills/or-task/SKILL.md` при триггере домена. Аналогично Vaultwarden-анлок для проектов на этой машине — скилл `/vaultwarden-unlock`. Вынос из CLAUDE.md в скиллы — экономия контекста: справочные детали грузятся только когда задача реально их касается, а не на каждой сессии.

Маршрутизация: механика/рутина → or-task.sh; код → opus-субагент; сложное/ревью → main. Приватные/корп репы во внешние API не роутить без отдельного решения пользователя; тихая замена исполнителя запрещена — проговаривать в чате.

## Karpathy Coding Guidelines (always-on, во всех проектах)

Базовые правила против типичных ошибок LLM при работе с кодом. Применять всегда; для тривиальных задач — по здравому смыслу. Полная версия — скилл `/karpathy-guidelines`.

1. **Think Before Coding** — не угадывай. Озвучивай допущения явно; если есть несколько трактовок — покажи их, не выбирай молча; если проще можно — скажи; если непонятно — остановись и спроси.
2. **Simplicity First** — минимум кода, решающего задачу. Без фич сверх запрошенного, без абстракций для одноразового кода, без «гибкости/конфигурируемости» которую не просили, без обработки невозможных сценариев. 200 строк, которые могли быть 50 → перепиши.
3. **Surgical Changes** — трогай только то, что нужно. Не «улучшай» соседний код/комментарии/форматирование, не рефактори рабочее, держи существующий стиль. Чужой dead code — упомяни, не удаляй. Каждая изменённая строка должна напрямую следовать из запроса.
4. **Goal-Driven Execution** — определи проверяемый критерий успеха до реализации и крути до его выполнения. «Исправь баг» → «напиши тест, воспроизводящий баг, потом сделай зелёным». Для multi-step — короткий план «шаг → проверка».

## CLEAR — самопроверка результата перед выдачей (always-on, во всех проектах)

Перед тем как выдать нетривиальный результат (research, код, план, фактическое утверждение, сводку) — молча прогони его по CLEAR. Не прошёл пункт — чини; не можешь проверить — пометь явно («R не проверил: …»), не выдавай как факт. Юзер вызывает вручную: «проверь по CLEAR» / «CLEAR-check» → прогони и верни построчный вердикт ✅/⚠️/❌ по каждой букве + что чинить.

- **C — Correct** — фактически верно: числа, имена, пути, флаги, API существуют — проверь в коде/командой, не выдумывай.
- **L — Logical** — внутренне непротиворечиво, вывод следует из посылок, нет скрытых скачков.
- **E — Evidence-based** — подкреплено источником (файл:строка, вывод команды, дока), а не памятью/догадкой.
- **A — Aligned** — отвечает именно на запрос, в рамках scope, без отсебятины и недоделок.
- **R — Reproducible** — воспроизводимо: те же входы → тот же результат; шаги повторяемы, не случайны.

Дополняет Karpathy #4 (Goal-Driven): тот задаёт критерий ДО работы, CLEAR проверяет результат ПОСЛЕ. Для тривиального — по здравому смыслу.
