# /doc-model — пересборка док-системы проекта под AI

Цель: любая модель (от haiku до старших) за одно чтение понимает, где что лежит, куда класть новое, и не тянет лишнего — без потери ни одного правила и ни одного факта. Работай как PM: research и правки — субагентами, сам решаешь и ревьюишь.

## Режимы

- `init` (по умолчанию) — модели нет либо она рассыпалась структурно: фазы 1→8 целиком. Заканчивается установленными механизмами (свежесть, стартовый пакет, заполнение), а не последним применённым файлом.
- `refresh` — модель есть, надо найти и починить дрейф: фаза 6 (линтер + stale), затем адресная починка красного. Фазы 1-2 не повторять, cold-start не пересобирать, но стартовый пакет (фаза 7) проверить ручным прогоном хука — нет или не срабатывает → поставить, это шаг refresh как и bootstrap линтера; секцию `заполнение` линтера и Stop-хук (фаза 8) — так же; ревью (фаза 4) — выборкой по изменённым документам, fleet-probe — только если правилась routing-таблица. Бюджет и критерий остановки назвать до работы.
- Механизма в репозитории ещё нет (каталога `<root>/.claude/doc-model/` не существует) — первый `refresh` начинается с bootstrap: поставить линтер и разметить ограниченный scope (L0, L1, файлы routing-таблицы), не все доки. Это шаг refresh, а не повод разворачивать фазы 1-3.
- Режим определяется до research'а. Запрос «доки протухли» — это `refresh`; молча подменять его полной пересборкой нельзя.

## Факты платформы (проверены замером 2026-08-25; сомневаешься — перепроверь дешёвым агентом)

- Субагент получает иерархию CLAUDE.md (глобальный → папка → проект) **снапшотом старта top-level сессии**, но НЕ контекст main-диалога. Explore/Plan-агенты не получают её вообще. Поэтому бриф всегда самодостаточен.
- Nested CLAUDE.md в подкаталоге авто-подгружается при чтении файлов оттуда — и main, и субагентам. Это главный рычаг path-scoped контекста.
- `.claude/rules/*.md` с frontmatter `paths:` — нативный механизм: грузится при работе с совпадающими путями.
- Рекомендация Anthropic: CLAUDE.md ≤200 строк; дубли убирать; детали — в path-scoped слой (docs: code.claude.com/docs/en/memory.md).

## Фазы

### 1. Research — 2 параллельных read-only субагента

a) **Инвентарь** (haiku): все знание-файлы (CLAUDE.md всех уровней, доки, планы, README, settings): путь | строки | байты | назначение в 1 строку. Посчитать cold-start bundle — что новая сессия ОБЯЗАНА прочитать по текущим правилам, в байтах: это метрика «до».
b) **Потребители и дубли** (opus, effort medium): какие hooks/скрипты (project settings.json + глобальные ~/.claude) какие файлы инжектят/читают/пишут; какие правила повторяются в 2+ местах и где формулировки РАСХОДЯТСЯ (цитаты файл:строка); что субагент не видит автоматически. Это blast-radius: доки — общий интерфейс всех сессий, ломать потребителей нельзя.

Отчёты — в служебный каталог задачи, не в контекст.

### 2. Модель — решаешь сам, фиксируешь в plan.md ДО правок

Принцип «один факт — один дом»; всё остальное — ссылка. Четыре слоя по механизму доставки:

| Слой | Носитель | Содержимое |
|---|---|---|
| L0 | корневой CLAUDE.md ≤10KB / ≤200 строк | миссия кратко, инварианты, ЕДИНСТВЕННЫЙ cold-start, ЕДИНСТВЕННАЯ routing-таблица «тип факта → файл», остальное указателями |
| L1 | nested CLAUDE.md по подкаталогам + `.claude/rules` с `paths:` | специфика слоя, ссылка на L0, без копий |
| L2 | данные: реестры/планы/доки | читаются адресно (строка/раздел), не целиком |
| L3 | derived (инжектируемые роутеры/индексы, стартовый пакет) | только маршрутизация, ноль правил, лимит ~25 строк на роутер, ~40 на пакет |

Cold-start живёт на двух носителях: шаги — текстом в L0, а свежесть/состояние/кто где/маршрутизация — стартовым пакетом, который хук приносит в контекст до первого действия (фаза 7). Текст «прочитай README и проверь claims» — дисциплина, и у новой сессии, которая ещё ничего не читала, она не срабатывает; пакет — механизм.

Каждому правилу старых доков назначь единственный дом. Создай `<root>/.claude/pm/_subagent-brief.md` — блок, который main вставляет в каждый бриф: scope, opsec, evidence-дисциплина, формат отчёта, строка ESCALATE. Правило анти-разрастания — в сам L0: новое правило кладётся в единственный дом по таблице; в CLAUDE.md попадают только инварианты уровня репо.

### 3. Применение — сначала черновики, потом живые файлы

- Draft-агенты пишут ЧЕРНОВИКИ в служебный каталог + **mapping-аудит**: каждое нормативное утверждение старых доков → keep-inline / moved-to:<путь> / link / drop+причина. Потеря без строки маппинга = провал задачи. Маппинг не выбрасывается после verify: сохраняется архивом для следующей пересборки (фаза 6).
- Черновики и mapping читаешь САМ (trust but verify), фиксишь, затем применяешь: полные файлы — заменой с бэкапом старого; точечное — apply-агентом по спеке «СТАРЫЙ→НОВЫЙ дословно, якорь — текст, не номер строки; не нашёл дословно → ESCALATE, не подгоняй».
- Файлы, которые инжектят хуки, вычисти от накопленного мусора; append-хуки без дедупликации почини на самозаменяющиеся. Verify: 3 прогона подряд → ровно одна метка.

### 4. Verify — независимый ревьюер

Read-only, рубрика единственная — «ни одно правило не потеряно и не ослаблено»: выборка 15-20 утверждений из бэкапа → у каждого есть дом (проверять сами файлы, не mapping); указатели ведут на существующие разделы; данные (статусы/даты/ID) не изменены; default-FAIL при сомнении. FAIL → фикс → точечный re-check только упавших пунктов. К пользователю с FAIL не выходить.

### 5. Fleet-probe — валидация боем

3-6 доменных read-only агентов по реальным областям проекта, каждому 3-4 вопроса: где статус его домена; где план и next action; куда записать новый факт такого-то типа; предметный вопрос по коду/материалам. Требуй источники файл:строка + список прочитанного + «чего не хватило для навигации». Провалы навигации → фиксы модели; предметные находки (расхождения статусов и планов) → списком пользователю; статусные документы без его решения не править.

### 6. Свежесть — механизм вместо дисциплины

Модель протухает молча: код, инфраструктура и договорённости меняются, документ остаётся прежним. Правило «обнови доки» этого не ловит, ловит только проверка, которую нельзя не заметить. Это ядро режима `refresh`; init без неё не закончен.

- **Живой реестр — сама routing-таблица L0.** Отдельный реестр домов с дословными якорями не заводить: он рвётся на каждой переформулировке живого правила, после чего якоря начинают чинить пачкой и проверка перестаёт что-либо проверять. Mapping-аудит фазы 3 сохраняется архивом в `<root>/.claude/doc-model/mapping-<дата>.md` — доказательство «ничего не потеряно» и вход следующей пересборки, вручную не поддерживается.
- **Линтер структуры** — `scripts/doclint.py` из каталога скилла (stdlib; конфиг `<root>/.claude/doc-model/config.json`), sources-разметки не требует, работает сразу после init: L0 и derived-роутеры в пределах лимитов (список derived — в конфиге линтера); каждый каталог верхнего уровня имеет дом в routing-таблице (вложенные репозитории, `_archive` и артефакты — в ignore-список); указатели ведут в существующие файлы и `#якоря`. Проверяются markdown-ссылки и конкретные относительные пути; плейсхолдеры `<...>`, глобы, пути вне репозитория и ссылки прозой пропускаются, иначе отчёт утонет в ложном красном. Автоматически пропускаются также внешние host/module-идентификаторы (`git.example.com/org/backend`), плейсхолдеры `YYYY` и пути, разрешающиеся внутри вложенных репозиториев (`internal/db` зелёный при существующем `<nested>/internal/db`); остальное — через `link_ignore_prefixes`. Лимиты L0 и derived переопределяются в конфиге (`l0_limits`, `derived[].lines`): байтовый лимит для кириллического L0 ставится с поправкой на два байта на символ (≈13 KB при тех же 200 строках), а не режется текст ради числа; derived-роутер растёт со строками таблицы, лимит — по числу slug, не по прозе. Дешёвый бонус: дословный дубль строки длиннее 60 символов в двух и более канон-файлах. «Один факт — один дом» по смыслу и «правило не ослаблено» механически не проверяются и остаются за ревью.
- **Что размечается** — файлы, которые routing-таблица L0 называет домом факта, независимо от слоя. Управленческий канон и реестры протухают быстрее всего, а CLAUDE.md и rules гниют мало и уже закрыты структурной проверкой; планы, handoff и рабочие материалы — вне разметки.
- **Где живут метаданные** — sidecar-каталог `<root>/.claude/doc-model/freshness/` (файл на документ), а не шапки самих документов: файлы L0/L1 инжектятся в каждую сессию, служебные поля в них съедают cold-start-байты. Поля: `sources` (глобы либо `external`), `reviewed` (дата), `review_after` (дней); схема — `references/freshness.md`.
- **Два триггера stale, не один.** Изменился объявленный вход (хеш либо `git log -1` по `sources`) — либо `reviewed` старше `review_after`. Второй обязателен: факты внешней природы (прод, созвоны, договорённости, внешние системы) из файлов репозитория не выводятся, hashable-входа у них нет, и без срока такой документ вечно зелёный. Для них `sources: external` плюс срок; фиктивные пути не выдумывать.
- **Снятие stale — только смысловое ревью** человека или main: перечитать документ против изменившегося входа, затем `doclint.py --bless <файл>` пересчитывает хеши и ставит дату. Скрипт, хук и CI не благословляют никогда — автоснятие превращает зелёный цвет в ложь.
- **Для документов `external`** смысловое ревью — read-only сверка агентами против прода/каталогов: таблица ✅/❌ с командами-доказательствами в служебный каталог задачи; main чинит ❌ и только потом `--bless`. Bless по памяти или по чужому summary — запрещён.
- **Прогон всегда report-only** (`exit 0`, печать). Блокирующий хук давит сессию к зелёному, а самый дешёвый путь к зелёному — подогнать метаданные. Прикрепление — блок свежести стартового пакета (фаза 7), то есть хук `SessionStart`: стейл нужен до работы, а не после. Печать из стартовой обёртки перед `exec claude` уходит в терминал человеку, модель её не видит (замер 2026-09-22) — обёртка не заменяет хук; дальше CI на push. Нет ни того, ни другого → печать возраста последнего прогона из стартового скрипта тоже механизм, а чистое «запусти руками» записать в L0 честно.
- **Массовое красное на первом прогоне — норма, а не работа.** Красных больше десятка → не чинить молча: триаж списком пользователю, ложные срабатывания — в ignore-конфиг. Документ под ограничением записи (чужой claim, `canon:*`) чинится докладом, а не правкой. Всё остальное красное чинится в том же прогоне по источнику: документ с `sources` приводится к коду и файлам каталога (для runbook код — истина, документ его описывает), а не откладывается «владельцу посмотреть»; к пользователю уходит только противоречие в самом источнике, правило или намерение — не факт. Незакоммиченные файлы правятся, когда пользователь дал добро на прогон refresh; без него — докладом.
- **Граница с `ground-truth`**: здесь — свежесть структуры доставки контекста (где что лежит, что читать на старте, дом факта); истинность предметных утверждений о поведении кода — там (STATUS.yaml, proof-цикл). Предикат выбора: факт проверяем тестом или кодом → `ground-truth`, факт о том, где что лежит → `doc-model`. В репозитории с установленным `ground-truth` его файлы sources-разметкой не дублировать.

### 7. Стартовый пакет — cold-start как механизм

Ради этого модель и строится: новая сессия сначала видит, что свежо, что в работе, кто где и куда писать, и только потом действует. Это не текст в L0 (текст — дисциплина, она не срабатывает у сессии, которая ещё ничего не читала), а derived-блок, который хук `SessionStart` вычисляет при старте и кладёт в контекст модели. Без установленного и проверенного пакета ни `init`, ни `refresh` не закончены.

- **Носитель** — `<root>/.claude/scripts/orient.sh` (копия `templates/orient.sh`, блоки адаптированы под канон репозитория) + хук `SessionStart` в `<root>/.claude/settings.json` без matcher: пакет нужен на `startup`, `resume` и `compact` — после сжатия контекст теряет и claims, и состояние. Контракт, хук и проверка — `references/start-packet.md`.
- **Четыре блока, порядок фиксирован, ≤ ~40 строк / ~4 KB, ≤ 1 с**: (1) свежесть — `doclint --summary --tree`; (2) состояние портфеля — одна строка статуса/WIP из канона (файл — по routing-таблице L0), не пересказ; (3) кто где — активные claims (scope | сессия | режим | дата | цель, свежие сверху, лимит строк), без claims-протокола — `git worktree list`; (4) маршрутизация действий — указатели, не правила: cold-start-шаги L0, движение задачи (claim → план → write-back → release/handoff — файл контракта), «read-only без claim, запись — после claim».
- **Не дублировать то, что уже в контексте**: routing-таблица L0 подгружается платформой сама — в пакете только указатель на неё; derived-роутер задач (L3) печатается пакетом, только если его не инжектит другой хук (глобальные settings пользователя проверить в фазе 1b).
- **Ничего не хранит и ничего не решает**: всё вычислено из канона в момент старта; report-only, `exit 0`, никогда не bless; секреты, адреса, токены не печатает; падение одного блока не валит остальные; тяжёлые проверки (doctor claims на секунды) — не в пакет, а по запросу из cold-start-шага.
- **Проверка**: ручной прогон `echo '{"source":"startup"}' | CLAUDE_PROJECT_DIR=<root> bash .claude/scripts/orient.sh` — `exit 0`, строки/байты/время в лимите, все четыре блока на месте; затем живой старт или compact — вывод хука виден в контексте (`SessionStart hook success`). Без второго шага пакет не считается установленным.

### 8. Заполнение, анти-раздувание, ветвление — механизмы

Ради чего скилл: новая сессия знает всё нужное и не перегружена — читает 4 KB пакета и 30 строк шапки плана, а не 2000 строк лога и три handoff. Это держится не правилами «обновляй план» и «не раздувай», а тремя механизмами; без них модель протухает так же, как без проверки свежести.

- **Линтер, секция `заполнение`** (`check_pm`, конфиг `pm`): шапка плана (первые `header_lines`) содержит `Next action` — читающая сессия берёт шапку, не хвост лога; план не длиннее `plan_lines` (старый лог — в `archive/`, шапка остаётся); handoff-файлов на единицу не больше `handoffs_max` — handoff только для незавершённой передачи, законченное складывается в план; направление (`<slug>/`) без плана — сирота; deliverable в контейнере живёт и одним handoff, а закрытый — вовсе без него (INFO). Ветвление: `.claude/rules/*.md` без `paths:` — WARN, такое правило грузится в каждую сессию и это L0-байты под видом L1. Единицы — `<slug>/` и `<container>/<deliverable>/` (`_management`, `_research`); прочие `_`-каталоги служебные. Массовое красное на первом прогоне — триаж списком пользователю (фаза 6), чужие планы линтер и main не правят.
- **Stop-хук write-back** (`scripts/writeback-check.py`, контракт — `references/writeback.md`): сессия за ход изменила файлы репозитория, но не тронула ни один дом заполнения (`.claude/pm/**` + `writeback.homes` из конфига) → один раз за сессию хук не даёт закончить ход и просит write-back как `additionalContext` (подсказка, не ошибка). Второй раз молчит, при `stop_hook_active` молчит, окно «правки этой сессии» — от маркера, который пишет стартовый пакет. Чужие окна отсекаются только по времени, поэтому подсказка одна и советует «не твоё — просто заверши». Гейта на запись без claim скилл не ставит: он ломает параллельные окна и не ловит heredoc — решение пользователя.
- **Шаблоны** `templates/plan.md`, `templates/handoff.md` — шапка, которую проверяет линтер (`Обновлено`, `Next action`, scope, DoD), append-лог снизу. Ставятся в `<root>/.claude/pm/_templates/` (или заменяют существующий шаблон репозитория по решению пользователя); контракт заполнения — L1 pm-каталога, не L0.
- **Установка** (фаза 3 для init, шаг refresh для существующей модели): конфиг `pm`/`writeback`/`rules_dir` при отличии от дефолтов; хук `Stop` в `<root>/.claude/settings.json` (`python3 ~/.claude/skills/doc-model/scripts/writeback-check.py`); маркер старта — блок в `orient.sh` (в шаблоне есть). Проверка: `selftest.py` зелёный, на фикстуре хук подсказывает один раз и молчит при тронутом плане.

## Umbrella и вложенные репозитории

- Единица работы — один git-репозиторий: свои L0, `config.json`, `freshness/`, свой прогон. Umbrella-репозиторий вложенные репозитории не пересобирает и не линтит; `doclint.py --tree` печатает summary каждого вложенного, у которого модель установлена, и называет те, где её нет.
- Сессия внутри вложенного репозитория получает **и родительские CLAUDE.md** (платформа читает их от текущего каталога вверх). Поэтому L0 umbrella — только инварианты и карта репозиториев, а L0 вложенного не повторяет родителя ни одной строкой: `parent_canon: ["../CLAUDE.md"]` в его конфиге, и линтер ловит дубли с родителем.
- Кросс-репозиторный факт (где какой репо, кто владелец, какой протокол claims общий) живёт в umbrella один раз; вложенный на него ссылается. Обратных ссылок из umbrella на внутренности вложенного — нет, иначе umbrella гниёт при каждом их релизе.
- Параллельные окна: линтер и `--summary` read-only, гонок нет. Свежесть — файл на документ, `--bless` пишет атомарно: bless разных документов из разных окон и веток не конфликтует ни в рабочем дереве, ни при merge. Один и тот же документ из двух окон — под claims репозитория (2-3 окна протокол держит), своего лока скилл не вводит; ждать нельзя → ветка в worktree внутри репозитория и merge, после которого затронутые документы честно краснеют по хешам и проходят re-bless после ревью слияния. Derived-роутеры, которые пишут хуки, — самозаменяющиеся (фаза 3), их рост ловит лимит линтера.

## Чувствительные проекты — здоровье/дети/PII/корп

Определи ДО research'а, чувствителен ли репозиторий (медицина, дети, персональные кейсы, корп-данные). Если да:

- **Обезличивание по умолчанию**: в CLAUDE.md, планы, handoff, брифы и отчёты агентов НЕ попадают персональные данные — имена клиентов/пациентов/пользователей, контакты, диагнозы, датированные личные кейсы. Реальные случаи — только псевдонимами (client-A); маппинг псевдоним→человек живёт вне репозитория (`~/.config/<проект>/`, права 0600), в репо — только ссылка на факт его существования.
- Research/inventory-агентам в бриф — явный запрет: цитаты данных людей в отчёт не выносить, только агрегаты и структуру («12 записей клиентов», не сами записи).
- Внешние API-воркеры (OpenRouter/or-task.sh, любые сторонние модели) для содержимого таких реп запрещены без отдельного решения пользователя — только модели подписки.
- Память/хроника (auto-memory, claude-mem): проверь settings проекта — отключить либо убедиться, что в наблюдения не утекают персональные данные; найденное в памяти ПД — вычистить.
- В mapping-аудите дополнительная судьба фрагмента: «содержит ПД → не переносить в новый дом, а обезличить или вынести из репо» — отдельной строкой на каждый случай.
- Fleet-probe добавляет opsec-вопрос: агент обязан показать, что знает правила обезличивания и куда кладётся чувствительное. Воспроизвёл ПД в отчёте → FAIL домена, и это проверяет приёмщик (main), а не сам агент.

## Инструменты (каталог скилла)

- `scripts/doclint.py --root <repo>` — линтер структуры, свежести и заполнения одним прогоном, только stdlib, всегда report-only. `--summary` — строка для стартового скрипта, `--exit-code` — для CI, `--bless <doc>` — после смыслового ревью. Схемы `config.json` и `freshness/`, условия stale и подключение к старту сессии или CI — `references/freshness.md`.
- `scripts/writeback-check.py` — Stop-хук write-back (фаза 8), только stdlib; контракт — `references/writeback.md`.
- `templates/plan.md`, `templates/handoff.md` — шапка плана и handoff под проверку линтера (фаза 8).
- `templates/orient.sh` — шаблон стартового пакета (фаза 7): копируется в `<root>/.claude/scripts/orient.sh`, блоки состояния и claims адаптируются под канон репозитория; контракт и хук — `references/start-packet.md`.
- `scripts/selftest.py` — фикстура с мутациями (красное там, где должно; bless → зелёное; мутация входа → красное). Гонять после любой правки линтера.
- В репозиторий кладутся только `config.json`, каталог `freshness/`, архив mapping-аудита и адаптированный `orient.sh` с хуком; линтер живёт в скилле. Чужой пробный прогон — через `--config`/`--freshness` во временный каталог, без записи в репозиторий.

## Правила

- Данные не терять: всё старое либо остаётся, либо переезжает с указателем. Незакоммиченные файлы пользователя не трогать.
- Правки только в working tree; коммит — по запросу пользователя. Никаких следов AI.
- Конвенции проекта важнее общих best practices; специфичные механизмы репо (session claims, локальные протоколы) — предмет research'а, не предположений.
- Модели: инвентарь — haiku; research/drafts/apply — opus (effort medium); критическое ревью — opus, effort high.
- Метрика успеха `init`: cold-start bundle «после» ≤ «до»; каждое правило — ровно в одном доме; потребители (hooks/скрипты) работают; fleet-probe без провалов навигации; линтер зелёный по всем трём секциям (структура, свежесть, заполнение — массовое красное заполнения на первом прогоне отдано триажем); стартовый пакет прикреплён к `SessionStart` и проверен живым стартом, либо честно записан в L0 как отсутствующий; Stop-хук write-back прикреплён и проверен на фикстуре; CI на push либо явно записан как ручной.
- Метрика успеха `refresh`: линтер зелёный; стартовый пакет срабатывает (ручной прогон + живой старт); Stop-хук прикреплён; секция `заполнение` — красное починено в своём scope, чужое отдано триажем; у каждого размеченного документа объявлены `sources` либо `external` со сроком `review_after`; ни одного stale без строки в отчёте — починен либо назван с причиной, и причина только одна из двух: ограничение записи или противоречие в источнике.
