# Свежесть: схемы, команды, подключение

Инструмент — `scripts/doclint.py` (stdlib, Python ≥ 3.9). В репозиторий кладутся только `config.json` и каталог `freshness/` в `<root>/.claude/doc-model/`. Оба — sidecar: в сами документы служебных полей не добавлять, файлы L0/L1 инжектятся в каждую сессию и платят за каждый байт.

## config.json

Все ключи необязательны, отсутствующие берутся из встроенных значений.

```json
{
  "l0": "CLAUDE.md",
  "l0_limits": {"bytes": 10240, "lines": 200},
  "canon": ["CLAUDE.md", "management/CLAUDE.md", ".claude/pm/CLAUDE.md", ".claude/rules/*.md"],
  "derived": [{"path": ".claude/pm/_active.md", "lines": 25}],
  "ignore_dirs": [".git", "node_modules", ".worktrees", "_archive"],
  "coverage_ignore": ["*.png", "*.pdf", "package.json"],
  "duplicate_min_len": 60,
  "parent_canon": ["../CLAUDE.md"]
}
```

- `canon` — глобы файлов, которые считаются L0/L1: по ним идут проверка указателей, покрытие каталогов и поиск дублей. Не включать планы и L2-данные.
- `derived` — инжектируемые роутеры с лимитом строк.
- `coverage_ignore` — глобы файлов верхнего уровня, которым дом не нужен (артефакты). Вложенные git-репозитории пропускаются сами.
- `pm`, `rules_dir`, `writeback` — секция `заполнение` и Stop-хук; схема — `writeback.md`.
- `parent_canon` — для вложенного репозитория: файлы родительского L0/L1 (путь относительно корня, `../` допустим). Участвуют только в поиске дублей: строка, повторённая из родителя, — красная.
- `ignore_dirs`, `coverage_ignore`, `link_ignore_prefixes` — эти три списка дополняют встроенные значения, а не заменяют их целиком: пользовательские элементы добавляются к дефолтным.

## freshness/ — файл на документ

Каталог `<root>/.claude/doc-model/freshness/`, имя файла — путь документа с `/` → `__`, ведущая точка отбрасывается: `management__README.md.json`, `claude__pm___sessions.md.json`; поле `doc` внутри — источник истины. Один документ — один файл, поэтому bless из разных окон и веток не конфликтует и сливается без ручного merge.

```json
{
  "doc": "management/README.md",
  "sources": ["management/*.md", "org/_summaries/*.md"],
  "review_after": 14,
  "reviewed": "2026-09-22",
  "hashes": {"management/decisions.md": "sha256:…"}
}
```

Документ внешней природы:

```json
{"doc": "management/risks-and-blockers.md", "sources": "external", "review_after": 7, "reviewed": "2026-09-22"}
```

- `sources` — список глобов относительно корня (`**` допустим, пути внутрь вложенного репозитория допустимы) либо строка `external` для документов, чьи входы вне репозитория (прод, созвоны, договорённости). Фиктивные пути не писать: они дают вечно зелёный документ.
- Сборочный мусор внутри глобов входом не считается (`__pycache__`, `*.pyc`, `.DS_Store`, `node_modules`, `.venv`, `.git` и кэши тестов): иначе любой запуск python красит документ без изменения по смыслу. Список — константы `ARTIFACT_*` в `doclint.py`.
- `review_after` — дней до принудительного stale. Для `external` обязателен, для остальных желателен.
- `reviewed` и `hashes` — ставит только `--bless` после смыслового ревью. Руками не править, хуки и CI не вызывают.

Что размечать: файлы, которые routing-таблица L0 называет домом факта, независимо от слоя. Планы, handoff, рабочие материалы — нет.

## Что считается stale

| Условие | Сообщение |
|---|---|
| нет `reviewed` | `никогда не ревьюился` |
| любой файл из `sources` изменился, добавился или исчез после bless | `hash: изменились …` |
| `reviewed` старше `review_after` | `ttl: reviewed …, срок … дн` |
| `hashes` нет, хотя `sources` заданы | `входы ни разу не зафиксированы (--bless)` |
| `external` без `review_after` | `не протухнет никогда` |

Снятие stale: перечитать документ против изменившихся входов, поправить содержимое, затем `--bless <doc>`. Bless без чтения — ложь в отчёте. Запись атомарная, по одному файлу на документ: соседнее окно или ветка, благословившие другой документ, ничего не теряют и сливаются без конфликта. Один и тот же документ из двух окон — под claims репозитория; после merge веток затронутые документы краснеют по хешам — это верно, re-bless после ревью слияния.

## Команды

```
python3 ~/.claude/skills/doc-model/scripts/doclint.py --root <repo>              # полный отчёт, всегда exit 0
python3 ~/.claude/skills/doc-model/scripts/doclint.py --root <repo> --summary    # одна строка
python3 ~/.claude/skills/doc-model/scripts/doclint.py --root <repo> --bless management/README.md
python3 ~/.claude/skills/doc-model/scripts/doclint.py --root <repo> --exit-code  # CI: 1 при красных
python3 ~/.claude/skills/doc-model/scripts/doclint.py --root <umbrella> --tree  # плюс summary вложенных репозиториев
python3 ~/.claude/skills/doc-model/scripts/selftest.py                           # после правки линтера
```

Пробный прогон на чужом репозитории без записи в него: `--config` и `--freshness` на файлы во временном каталоге.

## Подключение прогона

Всегда report-only для сессии: блокирующий хук давит модель к зелёному, а самый дешёвый путь к зелёному — подогнать метаданные.

1. Старт сессии — первый кандидат, stale нужен до работы. Прогон — блок свежести стартового пакета (`<root>/.claude/scripts/orient.sh`, хук `SessionStart` без matcher — `startup`/`resume`/`compact`; контракт — `start-packet.md`), а не отдельный хук с голым `doclint`: пакет несёт ещё состояние, claims и маршрутизацию, и второй хук на тот же момент — дубль. Если у репозитория есть чужой push-доступ — хук в `settings.local.json` (не коммитится): закоммиченный хук — команда, которая исполняется у каждого, кто клонирует, и её может подменить любой, кто пушит.
   Стартовая обёртка (`start.sh`) печатает только в терминал — человеку это полезно, но в контекст модели попадает только вывод хука; обёртка хук не заменяет.
2. CI на push — `--exit-code`; для этого скрипт копируется в `<root>/.claude/doc-model/doclint.py` (копия дрейфует от скилла, обновлять руками) либо машина CI имеет доступ к каталогу скилла.
3. Нет ни того, ни другого — ручной прогон, и это записывается в L0 как есть; «механизм установлен» в таком случае не заявлять.

## Границы

Линтер видит структуру указателей и изменение объявленных входов. Он не доказывает истинность текста, не видит необъявленные связи и не знает состояния прода. Управленческие факты внешней природы ловит только `review_after`.
