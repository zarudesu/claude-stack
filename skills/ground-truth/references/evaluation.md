# Как проверить пользу и цену

Размер SKILL.md или число чтений не доказывают экономию. Инструментальный поиск,
автоматические правила, reasoning, output, повторные проверки и агенты тоже
стоят контекста/времени. Cache-read и cache-write — отдельные категории.

## Четыре статьи затрат

Учитывать отдельно: разработка скилла; установка в репозиторий; обычные задачи
с сопровождением; периодические аудиты/обновления инструментов. Цена одного
удачного прохода без повторов и исправлений — не цена завершённой задачи.

Безубыточность при сравнимом качестве:

`N × (цена задачи без GT − цена задачи с GT) > установка + аудит + миграции`

Цена задачи с GT уже включает сопровождение. Если разность нулевая/отрицательная,
токенной окупаемости нет. Скилл может быть оправдан предотвращёнными дефектами,
но это отдельная гипотеза: нужен измеренный выигрыш качества, не обещание.

## Минимальный эксперимент

Не запускать платный benchmark на каждом изменении. При решении о внедрении:

1. Взять несколько реальных типовых задач и задач на границах. Сравнить обычную
   навигацию/существующие правила и тесты с ПОЛНОСТЬЮ подготовленной памятью.
   Контроль сохраняет обычные доступные знания проекта; не делать его искусственно
   беспомощным. Короткий init не подменяет проверяемый продукт. Считать полную
   стоимость первоначального исследования отдельно, затем амортизировать.
2. Одинаковые исходные коммиты, модель, инструменты, критерии и независимые
   рабочие деревья; учитывать cache и автоматические инструкции. Не давать
   контролю скрыто читать GT-правило. Варьировать порядок запусков.
3. Проверять готовый diff внешним тестом/ревью, которое не видит название варианта.
   Считать реальные регрессии, пропущенных потребителей и время исправления.
4. Сохранить usage всех сессий, повторов и дочерних агентов. Сначала сопоставить
   качество, затем стоимость успешно законченной задачи. Несколько прогонов —
   пилот, не статистическое доказательство.
5. Наблюдать сопровождение на обычных задачах до расширения на все репозитории.
   При отсутствии выигрыша оставить короткое руководство и полезные тесты;
   не поддерживать контракт ради самого контракта.

## Что именно должно окупаться

Первая подготовка не обязана быть дешёвой. Сравнивать серии задач с новой сессией
каждый раз: одинаковая база кода, затем последовательные изменения и поддержание
обеих ветвей. Включить маленькую функцию, рефакторинг, межсервисную границу,
новую область и правку в другом окне без обновления docs. Проверять, что PM
и исполнитель получают нужные знания, а stale не превращается в ложный факт.

Обязательно считать tokens всех автоинструкций/пакетов, дочерних сессий, sync,
провалов и ремонтов; latency и I/O хеширования — отдельно. Нельзя выдавать
байты документов за точные токены. Текущий helper хеширует весь объявленный
scope, хотя модель читает только пакет: токенная и дисковая стоимость различны.

При положительной разности цен задач порог примерно
ceil((init + аудит + миграции) / средняя экономия завершённой задачи).
Это расчёт из наблюдений, не обещание фиксированной цены для огромного repo.
Сначала качество/непропущенные зависимости, затем стоимость при равном качестве.
Без usage реальных повторных задач писать «экономия не измерена».

## Локальный сбор usage

`python3 <skill>/pipeline/usage_report.py transcript.jsonl [other.jsonl ...]`

Читает существующие Claude JSONL и Codex token_count; модели не вызывает.
Предпочитает Claude result.modelUsage, иначе result.usage, иначе дедуплицированные
assistant message.id. Не складывает итог с сообщениями повторно. Для Codex берёт
последний cumulative total_token_usage; cached_input входит в input и вычитается
при выделении uncached. Reasoning входит в output и отдельно не суммируется.

Цена берётся только из явного `total_cost_usd`; без неё `null`, не ноль.
Это сообщённая логом API-эквивалентная цена, не счёт подписки. У неполного лога
видимые usage — нижняя граница, дочерние агенты могут быть не включены.
Не передавать одновременно родительский итог и его дочерние логи:
автоматически распознать их перекрытие этот инструмент не может.
Несколько продолжений одной сессии в одном файле тоже нельзя бездумно суммировать:
последний cumulative result используется как итог с предупреждением.

Неизвестный формат/битые строки помечаются; общий полный итог не объявляется,
если часть стоимости неизвестна. Один файл — одна измеряемая единица.
Workflow totalTokens без разбивки сохранить как агрегат, не переводить в доллары
по выдуманному среднему тарифу. Отчёт агрегатов Workflow пока формировать из
родного результата: usage_report не обещает поддержку всех форматов журналов.
