# init: тщательная подготовка, обязательная приёмка

Не оптимизировать первый проход сокращением согласованного охвата. Оптимизировать
повторное использование результатов и отсутствие повторного исследования.
План и артефакты фаз сохранять вне автоматически загружаемого контекста.
Бюджет/недоступный сервис могут ограничить завершение, но результат тогда PARTIAL.

## 1. Границы и инвентарь

Прочитать локальные инструкции, карту репозиториев/сервисов, manifests, запускаемые
приложения, CI, генераторы и историю незавершённого исследования. Установить
фактические git-корни, отдельные checkout и worktree (git common dir), места
развёртывания и связи с внешними проектами. Один сервис может жить в нескольких
репозиториях, один репозиторий — содержать несколько приложений.
Не считать число worktree количеством сервисов.

Зафиксировать весь согласованный охват, недоступные части, исключения с причинами
и неизвестные внешние зависимости. В монорепо выделить frontend/backend/apps/
панели/shared/config/CI/операционные области. В экосистеме вести один реестр
репозиториев и межрепозиторных связей, STATUS — при необходимости в каждом repo.

Инвентаризировать исходники, тесты, схемы, миграции, конфигурацию, зависимости,
скрипты запуска/деплоя, документацию, правила и их потребителей. По умолчанию
watch=["."]; vendor/build/бинарные ресурсы исключать мотивированно. Игнорируемые
но значимые runtime-настройки представить безопасным versioned контрактом,
не чтением секретов. Не выдавать автоматически исключённое за проверенное.

## 2. Восстановление проверяемого знания

Исследовать все смысловые области, не только упоминания уже существующих доков.
Использовать manifests, маршруты, imports/callers, схемы, migrations, tests,
точки запуска и конфигурационные ветви. Сопоставить намерение документации и
поведение кода. Для важных выводов — путь/символ, проверка и границы применимости.

В каждой области сохранить:
- назначение, публичный контракт, входы/выходы, источник истины для данных;
- entrypoints, зависимости и потребители, важные end-to-end потоки;
- инварианты, совместимость, ограничения и rationale, опасные типовые изменения;
- существующие примитивы/модули, которые переиспользовать при новой функции;
- команды проверок и свидетельства, непроверенное, открытые решения и долги.

Проверить обе стороны межрепозиторных API/event/schema/cache/config связей:
producer, consumers, версия/формат, invalidation, failure modes. Не выводить
полноту runtime-графа только из imports. Внешние факты маркировать областью,
свидетельством и сроком, если применимо; без доступа — unknown, не fabricated.

Для большого проекта разделять независимые области между агентами, если среда
и полномочия допускают. Координатор выдаёт границы и артефакты, объединяет
пересечения и пропуски; не требует от каждого агента снова читать весь проект.
Нет обязательной конкретной модели или внешнего сервиса.

## 3. Сборка костяка

Применить [организацию знаний](doc-model-bridge.md): переиспользовать правильные
документы, устранить противоречия и дубли без потери требований, создать небольшие
канонические области. Из исследовательских артефактов собрать
[model.yaml](project-memory.md), а не ещё одно повествовательное резюме.

Разбивать область по смысловой границе/контракту, не произвольному числу файлов.
Публичный протокол и внутренняя реализация могут быть разными областями:
потребитель зависит от протокола, если это действительно полная его зависимость.
Широкий источник или ребро безопасны, но инвалидируют больше знаний; слишком
узкие дают ложную актуальность. Не сужать их только ради зелёного/дешёвого sync.

Каждый наблюдаемый файл должен быть отнесён к области либо явно исключён.
Принадлежность файлу не доказывает, что все его смыслы описаны: это проверяет ревью.
Для существующих важных утверждений/инвариантов использовать STATUS и реальные
checks, без claim на каждый helper. Новые implemented/partial доказать мутацией
в изоляции. Не ремонтировать найденные продуктовые дефекты вне запроса.

## 4. Установка и доступность

Прочитать [install.md](install.md), получить i9_install --facts и dry-run,
сопоставить локальные изменения; установить tools/rule/hooks/CI в согласованной
области. Установщик не заполняет model.yaml и не подтверждает её автоматически.
При новом run использовать pipeline/run.example.json и gt.py команды.

В каждом рабочем репозитории инструменты и маленькое правило должны быть
доступны новой сессии. Для общей модели добавить .ground-truth/workspace с
относительным путём к корню экосистемы; либо модель обнаружится у предка.
Не дублировать саму базу знаний в каждом репо. Для хоста без этих hooks добавить
эквивалентный вызов start/check в его workflow; не утверждать, что все клиенты
автоматически читают .claude/rules. Проверить фактический PM/исполнитель handoff.

CI должен checkout все зарегистрированные репозитории по воспроизводимым ревизиям
в ожидаемые относительные пути и запускать gt_context.py check. Шаблон CI
одиночного repo не умеет выбирать межрепозиторные версии: настроить это явно.
Для workspace без STATUS нужен отдельный memory-check job, а не фиктивный STATUS.
Текущий i9_install ориентирован на STATUS: он также добавляет bridge tests и
contract CI. Для memory-only области использовать нужные assets tools/rule/hooks
и отдельный memory job адресно, не добавлять неработающий bridge ради шаблона.
Отсутствующий обязательный checkout не обходить исключением ошибки.
Task worktree использует собственную модель с верными путями и локальными
receipts; нельзя брать «зелёное» от соседнего canonical checkout.

Установку завершить ДО записи receipts: rules/CI/tools — тоже входы и должны
попасть в подходящую область. Начинать с advisory, затем проверить и явно
включить требуемый blocking. CI должен сохранять fail-closed независимо от hooks.

## 5. Приёмка, без которой init не завершён

- Coverage: нет необъяснённых gaps; все согласованные приложения/репозитории
  представлены, их границы/исключения/unknowns отражены.
- Смысл: независимый проверяющий видит исходники и канонические документы,
  проверяет критические связи и mapping требований. Не только автор ставит OK.
- Доказательства: реальные проверки контрактов, baseline→mutation→restore;
  missing/skipped/error не назвать зелёным. Claims не заменяют обзор карты.
- Новые сессии без контекста автора: локальная задача, межобластная задача,
  задача на границе репозиториев (где есть) получают правильные источники,
  переиспользуемые примитивы и потребителей из пакета. Проверять результат,
  а не число вызовов rg. Доступная модель/PM как в реальной работе.
- В изоляции изменить код, документ, новый/удалённый файл и зависимость:
  stale обнаруживается; старый пакет не выдаётся как свежий; проверенный
  локальный sync восстанавливает только нужное. Проверить clean committed
  изменение, отсутствующий repo, начало нового сеанса и CI nonzero на дрейфе.
- После исправления найденного и семантического ревью получить revision;
  выполнить refresh --all --reviewed --expect REV --evidence с фактическим
  результатом ревью, затем check и повторить релевантные свежие task packets.
  Ключ не является заменой предыдущих пунктов.

Отчёт READY допустим, если пройдены все применимые пункты. Иначе перечислить
PARTIAL и конкретные ограничения, даже если hash-check зелёный. Записать
затраты init отдельно; экономия будущих сессий — ещё проверяемая гипотеза.
