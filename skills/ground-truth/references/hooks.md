# Хуки и CI

Хуки — локальная обратная связь, не доказательство всей программы и не замена CI.
Сначала advisory и проверка целевого окружения. Сохранять существующие настройки.
Текущая политика определяется SKILL.md и process.md; старые Dxx — история.

## Установка

i9_install собирает факты репозитория и показывает dry-run. --write может менять
tools/ground_truth, .claude/hooks, .claude/rules/ground-truth.md, настройки,
bridge-тест, CI и gitignore. Проверить diff до применения и локальные доработки
после него. Если .claude/ исключён, установщик использует локальные настройки;
не заставлять пользователя коммитить исключённые файлы.

Массивы Stop, SessionStart и PreToolUse мержатся по команде, не заменяются
целиком. Команда с поясняющим trailing comment считается тем же хуком.
Существующий timeout не уменьшается. Новые шаблонные timeout — Stop 600,
SessionStart 60, PreToolUse 30 секунд; это предел хоста, не ожидаемая стоимость.

Интерпретатор: GT_PYTHON, иначе .venv/bin/python, иначе python3. Нужны PyYAML
и зависимости проверяемых тестов. jq имеет Python fallback.

## SessionStart

Сначала gt_context.py hook --event start: текущая свежесть всей модели, включая
соседние репозитории и уже закоммиченные изменения. Ни LLM-вызовов, ни refresh.
Работает и без STATUS при наличии установленного helper. Старый пакет не
подтверждается прошлым логом. Missing model/checker error видны при старте.

Сбрасывает локальные session acknowledgements, печатает четыре кратких пункта
о поведении, области и доказательствах. Один verify --mode=sync --show-warn,
не два. На зелёном выводит максимум три предупреждения и команду для остальных.
Показывает текущий отказ, но не запрещает начать сессию и не приписывает его
автоматически предыдущему автору.

## PreToolUse

По умолчанию немедленно разрешает edit: GT_STRICT_EDIT_GUARD не установлен.
Для сохранённого legacy-режима явно задать GT_STRICT_EDIT_GUARD=1 в окружении
хост-процесса. Тогда работают прежние gates: blast acknowledgement для covered
файла, claim для uncovered файла внутри roots, бюджет переписывания зелёных
probes. GT_PROBE_BUDGET переопределяет старый бюджет (по умолчанию 2).
Это опциональная политика команды, не универсальный критерий правильности.

Проверка происходит на результирующем состоянии через Stop/CI независимо от
того, каким инструментом сделана правка. Написание нового helper само по себе
не требует новой записи контракта. Coverage claims и полнота модели — разные вещи.

## Stop

stop_hook_active=true предотвращает повторный цикл. Во всех остальных событиях
сначала gt_context.py hook --event stop, ДО clean-tree/STATUS shortcuts.
Stale: advisory предупреждает, blocking возвращает 2. Missing model/ошибка
проверяющего — 2. Никакой автоматической записи receipts.
Это обнаруживает также clean committed дрейф и правки зарегистрированного sibling.
Затем при грязном дереве с STATUS запускается прежняя проверка claims:

1. verify --mode=sync — согласованность контракта.
2. gt_session_guard --mode hook — проверки затронутых implemented/partial,
   описание мутации новых/повышенных claims. Саму мутацию хук не применяет:
   WARN явно оставляет доказательство для CI/изолированной приёмки.
3. remap_line_refs --check --base HEAD — предупреждение об устаревших цитатах.

Зелёный guard не скрывает WARN о неполном бюджете. Advisory печатает реальные
провалы, но возвращает 0; blocking возвращает 2. Третий последовательный красный
Stop в blocking добавляет ESCALATE. Это технический backstop: основная сессия
диагностирует повторяющийся отказ раньше, а не механически повторяет патчи.

Hook guard ограничен 25 проверками и 120 секундами между проверками; один
check может занимать до своего timeout. Неполнота/внутренняя ошибка — WARN,
не сертификат успеха. Эвристика «новое имя функции не найдено в тестах» —
предупреждение для ревью, не основание заблокировать корректный integration test.
Ошибка remapper не блокирует локальную работу и явно показывается.

## CI

Скопированный job обязан наследовать окружение тестов проекта: зависимости,
toolchains, необходимые переменные и пригодную историю git. Проверять в
реальном CI-образе. Не считать успех на машине автора проверкой CI.

Минимальный gate:

- gt_context.py check (отдельно, не внутри исполняемых claim checks);
- verify.py --mode=full;
- gt_session_guard.py --mode ci --base <полная база изменения>;
- согласованный mutation selfcheck --strict при acceptance/изменении канареек.

Установщик сохраняет legacy CI job с более широким mutation selfcheck.
Его частоту уменьшать только отдельным ревью после проверки выборочного guard.
По умолчанию CI guard не ограничивает число checks, временной предел — 3600s;
явные --max-checks/--budget-seconds допустимы, но непроверенный остаток — FAIL.
Внутренняя ошибка, missing base и недоступный toolchain также не дают зелёный CI.

GT_BASE_REF задаётся базой PR/MR или согласованным диапазоном push. HEAD~1 —
только fallback для простых изменений, не доказательство всего многокоммитного PR.
Структурный verifier содержит мягкие fallback-проверки старых контрактов:
обязательный CI должен запускать и session guard, не только verify full.

Memory-check вынесен отдельно намеренно: если проверять свежесть внутри каждого
поведенческого теста, любая mutation краснела бы от изменённого hash вместо
нарушения нужного поведения. Missing model/receipts/repo и stale дают nonzero,
независимо от advisory. Все зарегистрированные repos должны быть checkout в
воспроизводимых версиях; одиночный шаблон CI не собирает экосистему автоматически.
Хуки привязаны к git-репозиторию; для негитового зонтика запускать helper явно
из PM/workflow или из зарегистрированного child repo с workspace pointer.

Операции мутации выполнять в изолированном дереве, без параллельных читателей
того же файла. CI guard отказывает при dirty mutation target; --allow-dirty
доступен только отдельному selfcheck, не применять его
к занятому пользовательскому дереву. SIGINT/SIGTERM стараются восстановить файл,
но SIGKILL/авария процесса не дают такой гарантии.

См. process.md для проверяемой миграции и evaluation.md для стоимости.
