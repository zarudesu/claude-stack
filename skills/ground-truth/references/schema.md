# schema.md — полная схема STATUS.yaml

Это схема локальных исполняемых claims, не схема всей памяти проекта.
Карта областей, canonical docs, межрепозиторные зависимости и review receipts
описаны в [project-memory.md](project-memory.md). Полнота первичного init
определяется [init.md](init.md), не числом claims в STATUS.

Отвечает на вопрос: «какое поле куда, что обязательно/запрещено при данном `kind`, как резолвится `check`, что такое coverage/debt/edges/canary». Читать при написании/правке `STATUS.yaml` (Phase I.2, I.4, I.5, `sync`/`audit`), при споре о гранулярности claim'а, при разборе FAIL от `verify.py`, где сообщение указывает на конкретное поле/правило.

Нормативный источник — блок SCHEMA в задании сборки скилла, как поправлено D16/D19/D20 поверх `spec-final.md` §2.2. При расхождении с `spec-final.md` (там местами старый черновик схемы с `meta.visibility`, `check` без `check_kind`) — верно то, что здесь.

## 2. `meta`

| Ключ | Обязателен | Тип | Описание |
|---|---|---|---|
| `meta.repo` | да | str | информативно, обычно = имя git remote. Не проверяется верификатором по значению. |
| `meta.enforcement` | да | `advisory` \| `blocking` | режим Stop hook (см. `references/hooks.md`). Стартует всегда `advisory` (D8); переход на `blocking` — ручное решение main на `audit` (D21), не автоматика. |
| `meta.last_audited` | да | `"YYYY-MM-DD"` | дата последнего `audit`-прогона. |
| `meta.stale_after_days` | нет | int | окно для WARN по `live_state` (D27). По умолчанию `30`. |
| `meta.coverage.roots` | да | list[str] | директории — область действия coverage two-way (§4). |
| `meta.coverage.exclude` | нет | list[str] | fnmatch-глобы (posix-путь относительно корня репо), исключённые из coverage. Каждое исключение — с однострочной причиной рядом в комментарии/PR, не в самой схеме. |
| `meta.coverage.extensions` | нет | list[str] | какие суффиксы файлов считаются «исходным юнитом». По умолчанию `[".py", ".go", ".ts", ".tsx", ".js", ".sh", ".kt", ".java"]`. |
| `meta.coverage.runner` | да | `pytest`\|`go_test`\|`js_test`\|`junit`\|`none` | подсказка по умолчанию для новых claim'ов этого репозитория; не меняет резолюцию существующих `check_kind`. |
| `meta.banned_words` | нет | map | скоуп-исключения для D16-скана запрещённых слов, см. ниже. |
| `meta.banned_words.exclude` | нет | list[map] | список `{path, why}`: `path` -- fnmatch-глоб (posix-путь относительно корня репо, `*` пересекает `/`, как в `meta.coverage.exclude`); `why` -- обязательная непустая причина. Каждый элемент обязан иметь оба поля -- иначе `check_shape` FAIL. |

`meta.banned_words.exclude` сужает область D16-скана запрещённых слов
(`check_no_banned_words`) для файлов, где спорное слово -- часть предметной
области, а не след ассистента: например, сервис, который по имени
блокирует IP-диапазоны стороннего провайдера. Файл, чей relative posix-путь
подходит под `path` любого элемента, полностью пропускается и для FAIL-паттернов,
и для WARN-буззвордов. За каждый элемент, который совпал хотя бы с одним
файлом, `verify.py` печатает ровно один WARN
(`banned-word scan skipped N file(s) matching '<path>' (<why>)`); элемент,
не совпавший ни с одним файлом, тоже получает WARN
(`banned-word exclude '<path>' matched no tracked file`) -- мёртвое
исключение не должно молчать.

`STATUS.yaml` сам, всё дерево `tools/ground_truth/` и всё дерево `tests/`
никогда не могут быть исключены -- `check_shape` FAIL'ит с сообщением
`banned_words.exclude may not cover contract artifacts: <path>`, если
глоб пересекается с любым из них. Скан существует, чтобы держать чистыми
артефакты самого контракта -- разрешать дырку в них через exclude
бессмысленно и опасно.

## 3. `claims[]` — общие поля

| Ключ | Обязателен | Тип | Описание |
|---|---|---|---|
| `id` | да | str, snake_case | уникален в файле, стабилен: не переименовывается и не перенумеровывается задним числом (только добавляется новый). Единица адресации везде — `depends_on`, `see_also`, `debt.ref`, `edges.from/to`, кросс-ссылки из прозы `STATUS.yaml#<id>` (§13). |
| `component` | да | str | человекочитаемое имя компонента/факта. |
| `kind` | да | `status`\|`live_state`\|`out_of_repo` | закрытый список, ровно 3 значения (R1, spec §10). Определяет остальной набор полей — таблица §3.1. |
| `path` | зависит от `kind` | str \| list[str] | файл или директория (или несколько — §4.3). Обязателен фактически для `status`; для `live_state`/`out_of_repo` — опционален, но если задан, участвует в coverage/exists-проверке наравне со `status`-claim'ами. `:40-88`-суффикс на строке — курtezy-подсказка человеку, verify.py его игнорирует, никогда не проверяется как доказательство (spec §2.2/§4.1). Список путей остаётся **одним** чтением при навигации — открывается тот файл списка, который назван главным входом в `note` (§4.3). |
| `note` | **да** | str, непустая | почему такой статус, со ссылкой на код, не на намерение. `check_shape` требует непустую строку для claim'а любого `kind` — FAIL `note must be a non-empty string`, если поле отсутствует или пусто. |
| `why` | нет | str | указатель в research-артефакт (`"audit-2026-09-04#3"`). |
| `depends_on` | нет | list[str] | id других claim'ов ЭТОГО файла. Только смысловая связь внутри репозитория. |
| `see_also` | нет | list[str] | id других claim'ов, справочная ссылка. |

### 3.1 Поля по `kind` — закрытый список

| `kind` | обязательные доп. поля | запрещённые поля |
|---|---|---|
| `status` | `status`, `check_kind`, `check` | `command`, `pointer` |
| `live_state` | `command` | `status`, `check_kind`, `check`, `pointer` |
| `out_of_repo` | `pointer` | `status`, `check_kind`, `check`, `command` |

Проверяет `check_shape` (`contract_lib.py`) — FAIL при нарушении в любую сторону (недостаёт обязательного ИЛИ присутствует запрещённое). `attested` не вводится никогда (D6, A1 plan.md): десять проверяемых claim'ов лучше пятидесяти непроверяемых.

### 3.2 `note` — правила текста

`note` обязателен у claim'а любого `kind` (§3) и читается человеком и навигатором как первое объяснение статуса. Два правила про сам текст, оба — из поломок на прогоне:

**Не цитировать `CLAUDE.md:<строка>`.** Якорь вида `CLAUDE.md:214` протухает в том же прогоне, в котором поставлен: Phase I.8 переписывает навигационный слой, файл сокращается, и заметки начинают показывать на чужие или несуществующие строки (на прогоне — 4 штуки). Ссылаться на устойчивые якоря: путь к коду с именем функции/класса (`services/billing.py::refund_order`), имя теста, `STATUS.yaml#<id>` (§13), заголовок раздела дока — то, что переживает переформатирование файла. Номер строки допустим как подсказка рядом с таким якорем, но не как единственное содержание ссылки.

**Двоеточие с пробелом ломает plain-скаляр.** `note: поллер живой: wiring отсутствует` — не YAML: `yaml.safe_load` падает, `verify.py` завершается **exit 3** (поломка контракта, не расхождение — `references/verifier.md` §11), и весь файл перестаёт читаться из-за одной заметки. За одну правку это случилось дважды. Внутри plain-скаляра последовательности `: ` быть не должно — разделять части через `;` или `,`:

```yaml
  note: поллер живой; wiring в планировщике отсутствует, см. services/scheduler.py   # так
  # note: поллер живой: wiring отсутствует                                            # exit 3
```

Кавычки помогают, только если закавычен весь скаляр и внутри нет несбалансированных кавычек; надёжнее не писать `: ` вовсе — правило проще, чем разбор случаев.

## 4. `kind: status`

### 4.1 `status` — закрытый словарь, одна строка на значение

| Значение | Значит |
|---|---|
| `implemented` | код делает то, что заявлено, и это доказано `check`'ом прямо сейчас. |
| `partial` | часть заявленного работает, часть — нет; `note` называет границу, `check` доказывает работающую часть. |
| `stub` | заглушка выдаёт себя за реализацию (например `raise NotImplementedError`, no-op под видом рабочего пути) — заявлено в доках/сигнатуре, реально не делает ничего. |
| `absent` | заявленного пути в код вообще нет (например: мутирующая операция не зарегистрирована там, где по контракту обязана быть). `path` при этом указывает на существующий файл — где поведение обещано или должно быть зарегистрировано (док, реестр, CI-файл), не на отсутствующий файл: exists-проверка (§ниже) исключений для `absent`/`design-only` не делает. |
| `design-only` | описано (спека/дизайн), кода ещё нет и не планируется этим прогоном — не «забытая недоделка», а осознанно отложенное. |

Смена статуса **вниз** по доверию (`implemented`→`stub`) дешевле поверить, чем **вверх** (`stub`→`implemented`) — отсюда асимметричное правило 3-vote на Phase I.3 (`spec-final.md` §3.1, вне scope этого файла, см. `references/prompts.md`).

**Повышение статуса требует тронуть target `check`'а в том же изменении (D32).** `check_status_raise` сравнивает каждый `kind: status`-claim с базовой версией `STATUS.yaml` (`sync` → `HEAD`, `full` → `GT_BASE_REF`/`HEAD~1`): рост ранга (`absent`/`design-only` 0 < `stub` 1 < `partial` 2 < `implemented` 3) при посимвольно том же `check`, том же `check_kind` и ни одном изменённом файле, на который `check` указывает, — **FAIL**. Практика авторинга: поднимаешь статус — в том же коммите усиливай тест/пробу, которая это доказывает, либо переписывай `check` на реально более сильный (тогда его резолвимость проверит `check_collectible`). Понижение статуса, новый claim и смена `kind` под это правило не попадают; переименование `id` делает claim новым — не переименовывай `id` в том же изменении, что и повышение статуса. Детали и вырожденные случаи — `references/verifier.md` §14.

### 4.2 `check_kind` + `check` — синтаксис и резолюция (D17)

`check_kind` — явное отдельное поле (не префикс внутри строки `check`, это было отклонено как отход от D6 буквального решения владельца).

| `check_kind` | Синтаксис `check` | Резолюция в `sync` | Резолюция в `full` | Сила |
|---|---|---|---|---|
| `pytest` | node-id до функции/метода; несколько через `;` | AST без импорта | Реальный общий pytest selected checks с JUnit XML; отсутствие cases, fail/error/skip не дают успеха | Подтверждает выполненные assertions, не всю прозу claim |
| `go_test` | `path/to/package::TestName` | regex объявления | `go test -json -count=1 -run` и pass-событие выбранного теста; runtime skip не успех | Исполнение выбранного теста |
| `js_test` | `file.test.ts::test name` | regex test/it/describe | Реальный Node/Jest/Vitest; TAP/JSON отчёт о выбранном тесте; skip/нулевой запуск не успех | Исполнение выбранного теста; совместимость версии раннера проверить при миграции |
| `junit` | `fully.qualified.TestClass::method`; несколько через `;` | файл `<module>/src/test/java/<pkg path>/<Class>.java` существует и содержит `\bvoid\s+method\s*\(`; `<module>` — корень репозитория либо директория с `pom.xml` под ним (первая, чей `src/test/java` держит файл) | плюс реальный прогон: `mvn -q -B -DskipITs=true -Dsurefire.failIfNoSpecifiedTests=true -Dtest=<SimpleClass>#<method> test` в `<module>`, затем разбор `target/surefire-reports/TEST-<fqn>.xml` (§20 в `verifier.md`); нет `mvn` в `PATH` → проверка не выполнена, full FAIL | сильная: реально прогоняет тест и требует свежего surefire-отчёта — отчёт удаляется перед запуском, поэтому отчёт от прошлого прогона не может выдать себя за текущий |
| `probe` | относительный путь до скрипта (`tools/ground_truth/probes/<name>.py`) | файл существует **и** (исполняемый бит **или** валидный shebang в первой строке) | плюс реальный запуск: exit 0 = держится, exit 1 = сломано → FAIL, exit 77 = SKIP → full FAIL (не проверено) | сильная в узких рамках — реально выполняется, а не только существует |

**Почему без `importlib`.** Ранняя версия резолвера (`spec-final.md` §2.6, псевдокод) импортировала тестовый файл через `importlib.import_module` — падает на conftest/fixtures вне контекста pytest-раннера; CI-джоб ставит только `pyyaml`, реального pytest-окружения на этапе `sync` может не быть. D17 заменяет это на чистый AST-парсинг файла — ни импорта, ни тулчейна не требуется вообще для `sync`.

**Почему `check_collectible` вызывается всегда, без условий.** Ранний черновик демонстрировал баг: `run()`/`main()` вызывал `check_shape`+`check_coverage`, но не `check_collectible` — фантомный `check:` проходил зелёным. `run(root, mode)` обязан включать `check_collectible` в базовый набор `sync`, без исключений (spec §2.6, зафиксировано в контракте публичного интерфейса `verify.py`/`contract_lib.py`).

**Слабая проверка `go_test`/`js_test` — не второй источник правды.** Верификатор никогда не подтверждает, что тест ПРОХОДИТ — только что он существует там, где заявлено. Фактическое прохождение доказывает штатный `go test ./...`/`npm test` в CI (spec §2.3, антипаттерн-таблица §10 «Ложное покрытие через слабый check»). `junit` из этого правила выпадает: в `full` он не только резолвит объявление, а реально прогоняет тест через `mvn` и разбирает surefire-отчёт — сам отчёт и есть источник правды о PASS/FAIL, не регекс по объявлению.

### 4.3 `path`: строка или список (D19)

`path` — `str` **или** `list[str]`. Список — для claim'а, описывающего несколько файлов сразу (тематическая группа скриптов, см. §8 «гранулярность»). Каждый элемент списка участвует в coverage-проверке §4 независимо; claim считается covering-для-юнита, если ХОТЯ БЫ ОДИН элемент списка равен юниту или является его предком-директорией.

```yaml
- id: delivery_scripts_group
  component: "one-off delivery scripts (bulk send, retry queue drain)"
  kind: status
  status: implemented
  path:
    - "scripts/bulk_send_reminders.py"
    - "scripts/retry_queue_drain.py"
  check_kind: probe
  check: "tools/ground_truth/probes/delivery_scripts_importable.py"
```

**Чтение контекста.** Путь-список группирует связанные файлы; note указывает основной вход, если он есть. Читать столько, сколько нужно для задачи. Вывод поиска и автоматические правила тоже занимают контекст; ни grep, ни список из N файлов не являются «бесплатным одним чтением».

## 5. Coverage rule — two-way (D19)

Две независимые проверки в `check_coverage(root, data)`, не одна:

1. **Код → контракт** (orphan-код). Каждый «юнит» под `meta.coverage.roots` обязан быть покрыт claim'ом или явно в `exclude`.
2. **Контракт → код** (протухший claim). Каждый `path` каждого claim'а обязан существовать на диске.

### 5.1 Что такое «юнит»

Юнит = файл под одним из `meta.coverage.roots`, чей суффикс входит в `meta.coverage.extensions` (по умолчанию `.py .go .ts .tsx .js .sh .kt .java`), **минус**:

- совпадение с любым `fnmatch`-паттерном из `meta.coverage.exclude` (fnmatch по **posix-строке** относительного пути, не `Path.match` — `**` не работает в `Path.match` до Python 3.13, окружение это не гарантирует);
- любой путь, содержащий `__pycache__`;
- файлы, чей basename начинается с `test_` или заканчивается на `_test.<ext>` (тестовые файлы сами по себе не требуют claim'а — их покрывает `check`, указывающий НА них из claim'а тестируемого кода).

**Sanity-проверка самих `exclude`-паттернов.** Голый wildcard (паттерн, у которого после `pat.strip("*")` ничего не остаётся — `"**"`, `"*"`) — **FAIL** `meta.coverage.exclude entry is a bare wildcard` сразу, независимо от того, что он реально исключает: это заведомо не «причина рядом с исключением» (§5.4 пример 4), а попытка выключить coverage целиком. Паттерн, который совпадает больше чем с 90% файлов-кандидатов coverage-скана (до исключений), тоже **FAIL** `exclude should not swallow nearly the entire coverage scan` — тот же класс проблемы более узким паттерном.

### 5.2 Что такое «покрыт»

Юнит покрыт, если существует claim, для которого `unit == p` или `p` — один из `unit.parents` (через `pathlib`, отношение parent/equal), где `p` — любой элемент `path` этого claim'а (строка или элемент списка). **Никогда `str.startswith`** — ранний черновик матчил покрытие префиксом строки, что даёт баг: `app.py` «покрывает» `app2/foo.py` просто потому что строка `"app2/foo.py"` начинается с `"app"`. `pathlib`-отношение этого класса ошибок не допускает.

**`path` не может резолвиться в сам корень репо или в предка coverage root'а.** Если разрешённый `path` claim'а равен корню репозитория, или является предком одной из директорий `meta.coverage.roots`, — **FAIL** (`resolves to the repo root itself` / `is an ancestor of a coverage root`), до того как файл вообще попадает в проверку «покрыт». Без этого guard'а `path: "."` — легальный способ объявить один claim «покрывающим» вообще всё в репозитории, обнуляя orphan-детекцию из §5.2 не хуже голого `exclude: ["**"]` выше.

### 5.3 Обратная проверка

Для каждого claim'а с `path` (любой `kind`, не только `status`) — путь (каждый элемент, если список) обязан существовать относительно корня репозитория. Переименовали/удалили файл, claim остался → FAIL `path '<path>' does not exist`.

### 5.4 Разобранные примеры

**Пример 1 — чистое покрытие.**

```
meta.coverage.roots: ["services/"]
файлы на диске: services/invoice_reminder.py, services/report_worker_health.py
claims: path: "services/invoice_reminder.py"  (claim A)
        path: "services/"                    (claim B, каталожный уровень)
```
`services/invoice_reminder.py` покрыт claim'ом A (равенство) И claim'ом B (A — предок через `services/`). `services/report_worker_health.py` покрыт только claim'ом B (директория-предок). Coverage чист — второй файл не orphan, потому что claim B взял на себя весь каталог.

**Пример 2 — orphan.**

```
meta.coverage.roots: ["handlers/"]
файлы: handlers/order_commands.py, handlers/refund_commands.py
claims: path: "handlers/order_commands.py"
```
`handlers/refund_commands.py` не равен и не имеет claim'а-предка на всю `handlers/` → в `--mode=full` **FAIL** `handlers/refund_commands.py is not covered by any claim` (в `--mode=sync` та же находка — WARN с подсказкой `fix:`). Чинится либо новым claim'ом на `refund_commands.py`, либо переводом claim'а на каталог `handlers/`, если оба файла — один смысловой компонент.

**Пример 3 — протухший claim.**

```
claims: path: "services/invoice_reminder.py"   # файл переименован в services/reminders.py
```
Файла по старому пути нет → **FAIL** `path 'services/invoice_reminder.py' does not exist`, независимо от orphan-проверки (это отдельная, вторая часть two-way).

**Пример 4 — exclude.**

```
meta.coverage.exclude: ["scripts/one_off/**"]
```
Любой файл под `scripts/one_off/` не становится юнитом вообще — не требует claim'а и не может стать orphan. Каждое исключение — с однострочной причиной в том же коммите (spec §2.2), сам верификатор причину не хранит и не проверяет.

## 6. `kind: live_state`

Единственное поле сверх общих — `command`: как ПРЯМО СЕЙЧАС получить ответ (SSH-команда, API-запрос, grep деплой-конфига). **Никогда сохранённое значение** — это ядро A3 (plan.md): контракт не второй источник правды, `live_state` описывает, КАК проверить, не ЧТО сейчас. `note` может фиксировать результат последнего измерения с явной пометкой «замерено тогда-то, перепроверь командой выше», но это не заменяет `command`.

### 6.1 Stale live_state — WARN, не FAIL (D27)

Не полагается на ручную дату в тексте (регрессия одного из черновиков: сессия правит прозу заметки, не трогая дату рядом — гниёт незамеченным). Дата берётся из `git log`:

- **Границы блока** claim'а в файле — от строки, содержащей `- id: <id>`, до строки перед следующей `- id:` (или следующим top-level ключом файла, если claim последний).
- Команда: `git log -1 --format=%ad --date=short -L <start>,<end>:STATUS.yaml`.
- Нет вывода (файл не закоммичен, локальные незакоммиченные правки блока) → **skip**, не WARN и не FAIL — не с чем сравнивать.
- Дата старше `meta.stale_after_days` (по умолчанию 30) → **WARN** `live_state note last touched <date>, recheck it`. Никогда FAIL — это нудж перепроверить, не поломанный контракт (spec §2.6).

Проверяется только в `--mode=full` (дорогая операция, `git log -L` — не на каждый Stop).

## 7. `kind: out_of_repo`

Единственное поле сверх общих — `pointer`: где субъект реально живёт (другой git-репозиторий, вендорский продукт, внешний API). Используется, когда у ЭТОГО репозитория нет кода, который мог бы реализовать или подделать факт — попытка завести здесь `status` была бы unfalsifiable claim, запрещённым R2/A1.

Зависимость «мой компонент опирается на компонент в чужом репо» выражается этим же kind'ом: claim `out_of_repo` с `pointer` на тот репозиторий; если связь можно проверить, она дополнительно объявляется в `edges[]` с пробой (§9).

## 8. Гранулярность claim'а (D7, D22)

**Базовое правило (D7).** Уровень сервиса/пакета; вложенные claim'ы — там, где внутри реально смешаны разные статусы (часть пакета `implemented`, часть `stub`). Компонент в коде без записи → FAIL по coverage (§5) — это единственный жёсткий критерий «достаточно ли мелко»: слишком крупно — orphan не всплывёт вовремя внутри большого каталога; слишком мелко — разрастание (R1).

**Правило для множества похожих одноразовых файлов (D22, кейс «40 корневых скриптов»):**

| Класс скрипта | Решение |
|---|---|
| На него ссылается нормативное утверждение доков/cron/deploy-конфига («скрипт X шлёт рассылку по расписанию Y») | отдельный claim, `check_kind` по факту (обычно `probe`, если нет теста) |
| Тематически похож на другие, без отдельного нормативного утверждения | одна claim-группа, `path:` — список файлов (§4.3), один `check` на группу (например `probe`, доказывающий «все импортируются без ошибки») |
| Мёртвый код — нет потребителей (`blast_radius.py` не находит импортёров, не упомянут в cron/CI) | одна группа `status: implemented` (код есть и работает как написан) + `debt`-запись `description: "unreferenced, delete candidate"`, `severity: normal` — решение об удалении файла ждёт владельца, скилл сам файлы не удаляет без утверждённого списка (см. `references/doc-model-bridge.md` про workflow утверждения) |

**Несколько claim'ов на один файл — норма.** Один файл спокойно несёт два claim'а с разными статусами, если в нём смешаны разные предметы: живой путь и мёртвый рядом с ним, оплата `implemented` и возврат `stub`, поллер `implemented` и его wiring `absent` — все три пары встречались на прогоне. Правило разрешения: **`status` принадлежит concern'у, а не файлу.** Вопрос «какой статус у этого файла» некорректен; корректен «какой статус у этого поведения». Навигатор и грейдер выбирают claim по concern'у из формулировки задачи, а не по совпадению пути. `blast_radius.py` печатает `status` рядом с каждым claim'ом, попавшим на путь, — при двух claim'ах на файле видно оба, и выбор делается глазами, а не угадыванием.

**Чего при этом делать нельзя.** Два claim'а с **одинаковым `path` и одинаковым `check`**, но разными `status` (например, `migration_order_guard` `partial` и `migration_chain_validator` `implemented` на одном `scripts/check_migrations.py` и одном тесте) — это не гранулярность, а два ответа на один вопрос: один и тот же тест одновременно и доказывает, и не доказывает. Пару обязан поймать judge-synthesis на I.3.5; верификатор её не ловит — `check_shape` сверяет claim'ы только по `id` (§3) и `debt.id` (§10), совпадение `path`+`check` при разных `status` в его проверки не входит. Разрешается одним из двух способов: **merge** в один claim со статусом по слабейшей части — либо **разведение check'ов**, когда у каждого claim'а свой `check`, доказывающий именно его concern, плюс обязательные перекрёстные `see_also` и `note`, называющие границу между ними. Оставить как есть нельзя ни в одном варианте.

## 9. `edges[]` — кросс-claim/кросс-репо рёбра, обязательная проба

```yaml
edges:
  - from: invoice_reminder_sends_before_due     # id claim'а В ЭТОМ файле
    to: "mailer:send_api"                         # id claim'а ИЛИ "<внешний-репо/домен>:<свободный текст>"
    probe: "tools/ground_truth/probes/mailer_send_api_reachable.py"   # ОБЯЗАТЕЛЕН
```

| Ключ | Обязателен | Описание |
|---|---|---|
| `from` | да | id claim'а этого файла — резолвится в существующий id, иначе FAIL. |
| `to` | да | id claim'а (в этом файле или в другом, по конвенции `repo:id`) либо свободный текст с пометкой внешнего репо/домена. |
| `probe` | **да, без исключений** | относительный путь до exit-0/1 скрипта; обязан существовать и быть исполняемым. |

**Почему проба обязательна, а не опциональна.** Один из ранних черновиков допускал декларацию ребра голой строкой без пробы — ровно та unfalsifiable запись, которую A1/R2 запрещают (spec §2.5, «Расхождение и решение»). Статический анализ импортов принципиально не видит границу репозитория — пробе здесь замены нет. Разница с `depends_on`: `depends_on` — связь между claim'ами ОДНОГО файла, оба конца видны сразу, пробы не требует; `edges` — граница репозитория/сервиса, требует пробы всегда.

## 10. `debt[]` — структурный долг

```yaml
debt:
  - id: report_worker_health_needs_implementation   # уникален среди debt.id
    ref: report_worker_health_wiring          # ОБЯЗАТЕЛЕН: id claim'а, к которому относится долг
    description: "stub raises NotImplementedError; docs described it as live before this audit"
    severity: normal      # blocking | normal | cosmetic
    state: open           # open | accepted | resolved
    owner: ""             # пусто = не назначено, не "ничья проблема"
    opened: "2026-09-04"
```

| Ключ | Обязателен | Тип | Описание |
|---|---|---|---|
| `id` | да | str | уникален среди всех `debt[].id`. |
| `ref` | **да** | str | id claim'а. Не резолвится → FAIL `debt.ref unresolved`. |
| `description` | да (по конвенции) | str | что не так. |
| `severity` | да | `blocking`\|`normal`\|`cosmetic` | закрытый список. |
| `state` | да | `open`\|`accepted`\|`resolved` | процесс-состояние ЗАПИСИ О ДОЛГЕ, не вторая копия `claim.status`. |
| `owner` | да | str, может быть `""` | пусто ≠ отсутствие требования — значит «не назначено». |
| `opened` | да | `"YYYY-MM-DD"` | дата заведения. |

**Ключевое правило (не second source of truth, spec §2.2 «Расхождение и решение»):**

> `debt.state: resolved` — **FAIL**, пока `claims[debt.ref].status` остаётся в `{stub, partial, absent}`.

Это единственное, что не даёт `debt.state` стать второй правдой рядом с `claim.status`: закрыть долг без того, чтобы claim реально перешёл в `implemented`/`design-only`/`partial`-с-другой-границей, технически невозможно — верификатор красит такую попытку.

**Зеркальный случай — WARN только для `blocking`-долга (D33).** `debt.state` в `{open, accepted}`, пока `claims[debt.ref].status == implemented`: при `severity: blocking` — **WARN** `debt is <state> but claim <ref> is already implemented -- close the debt or explain why it is still open`. Противоречия в контракте нет (долг мог решиться, запись просто не обновили), но открытый блокирующий долг на claim'е, объявленном реализованным, — расхождение, которое стоит увидеть.

При `severity` `normal` или `cosmetic` верификатор молчит: такой долг на реализованном claim'е — обычная гигиена (рефактор, отсутствующий тест, улучшение поверх работающего кода), а не сигнал. WARN на каждой такой записи давал бы шум пропорционально длине списка долга — на прогоне это сотни строк, за которыми перестают читать остальные WARN'ы. В обоих вариантах, в отличие от `resolved`-при-stub, прогон не блокируется — решение «закрыть долг или оставить с объяснением» за автором.

## 11. `canary` + `mutation` — атрибут claim'а, не отдельный claim (D20)

```yaml
- id: invoice_reminder_sends_before_due
  component: "invoice reminder service"
  kind: status
  status: implemented
  path: "services/invoice_reminder.py"
  check_kind: pytest
  check: "tests/test_invoice_reminder.py::TestInvoiceReminder::test_sends_three_days_before_due"
  canary: true
  mutation:
    file: "services/invoice_reminder.py"
    find: "DAYS_BEFORE_DUE = 3"
    replace: "DAYS_BEFORE_DUE = 30"
  note: "also the canary for tools/ground_truth/gt_mutation_selfcheck.py -- move canary to another claim before removing this one"
```

| Ключ | Где | Обязателен | Описание |
|---|---|---|---|
| `canary` | на claim'е `kind: status` | нет (по умолчанию false/отсутствует) | `true` — этот claim участвует в мутационном самопроверке. |
| `mutation.file` | там же | да, если `canary: true` | файл, который патчится (обычно совпадает с `path`, не обязан). |
| `mutation.find` | там же | да | буквальная подстрока, ищется и заменяется ровно один раз. |
| `mutation.replace` | там же | да | буквальная замена. |

**Почему не отдельный claim-дубликат.** Ранний черновик заводил canary отдельной записью, дублирующей claim, который она проверяет, — второй claim на тот же код есть шанс разойтись с первым (те же риски §2.2 R3). D20: canary — атрибут СУЩЕСТВУЮЩЕГО claim'а. Минимум один `canary: true` на репозиторий обязателен (SC-b, `plan.md`). Протокол исполнения — `gt_mutation_selfcheck.py`, детали в `references/verifier.md` §«mutation selfcheck».

## 12. Гвард `docs/_human/` (D13, spec §4.2)

`path` и `check` **никогда** не могут резолвиться внутрь `docs/_human/**` — структурная проверка в `check_shape`, а не текстовое правило: попытка технически невозможна, не просто «не положена». Проверка сначала нормализует путь (`os.path.normpath` над posix-формой) прежде чем смотреть на части — `..`-переходы вида `foo/../docs/_human/notes.md` резолвятся в `docs/_human/notes.md` до сравнения, не проходят мимо guard'а лексической подстановкой. `docs/_human/` — карантин человеческой прозы (заметки, ретроспективы без actionable-содержания), не входная точка cold-start и не источник claim'ов ни при каких обстоятельствах.

## 13. ids и кросс-ссылки — конвенция `STATUS.yaml#<id>`

Проза (docs, комментарии, PR-описания) ссылается на claim как `STATUS.yaml#<id>` — не настоящий YAML-якорь, соглашение. `check_links(root, data, mode="full")` дополнительно сканирует tracked `*.md`-файлы репозитория на такие ссылки и проверяет резолвимость id (D27). Тот же id — универсальный ключ для `depends_on`, `see_also`, `debt.ref`, `edges.from/to`.

## 14. Анти-паттерны (spec §10, R1–R3) и как их не допустить в схеме

| Риск | Суть | Как схема этому не даёт случиться |
|---|---|---|
| **R1 — переусложнение** | DSL, новые `kind`, «гибкость про запас» | ровно 3 `kind` навсегда; `check_kind` — явное закрытое поле, не расползающийся набор ad-hoc ключей; `attested` отвергнут явно; ничего сверх полей §3–§11 не добавляется без нового D-решения. |
| **R2 — формальные проверки без силы** | `check` существует, но ничего не может провалить | `check_collectible` обязателен без исключений (§4.2); assertion-density lint (WARN, если у pytest-теста ноль `assert`) — см. `references/verifier.md`; canary/mutation обязателен минимум один на репо (§11). |
| **R3 — контракт как вторая правда** | `STATUS.yaml` описывает поведение своими словами вместо ссылки на код | `status` обязан нести `check`; `live_state` — только `command`, никогда значение (§6); `debt.state: resolved` невалиден без реального перехода claim'а (§10). |

**Правило-сигнал (spec §10, буквально):** если верификатору когда-либо понадобится `try/except`, чтобы толерантно проглотить непроверяемый claim, — это симптом R3, а не повод писать более снисходительный код. Лечится сменой `kind` claim'а (обычно `status`→`live_state`, если факт на самом деле не статичен, или `status`→`out_of_repo`, если код здесь в принципе не может это доказать), никогда добавлением терпимости в `contract_lib.py`.
