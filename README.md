# claude-stack

Рабочий сетап [Claude Code](https://claude.com/claude-code) — главная сессия работает на модели Fable 5.1, субагенты по умолчанию — на Opus 5.5; собран вокруг трёх идей:

1. **Main session — decider, а не печатная машинка.** Главный поток думает, планирует и ревьюит; весь код и все правки пишут дешёвые субагенты. Правило текстовое, в глобальных инструкциях; хук-гейт на `Edit`/`Write` в главном потоке был и снят: правки через Bash он не видел, поэтому реальные записи проходили мимо него.
2. **Токен-экономия — дисциплина, а не оптимизация постфактум.** Матрица моделей по сложности задачи, эскалация вместо угадывания, внешние дешёвые воркеры под рутину, `/clear` на границе задач.
3. **Память — на диске, а не в контексте.** Состояние задач, факты о проекте и хроника сессий разнесены по разным файлам с чёткими границами: что где лежит и кто это пишет.

В репозитории — переиспользуемые куски этого сетапа: скиллы, агенты, хуки и скрипты. Ничего специфичного для конкретной компании или инфраструктуры здесь нет — это методология и тулинг, конфиги подставляются под свой проект.

Рассчитано на опытных разработчиков, которые уже работают с Claude Code и хотят собрать похожий контур себе.

Живая версия страницы: [claude.zardes.dev](https://claude.zardes.dev). Репозиторий: [github.com/zarudesu/claude-stack](https://github.com/zarudesu/claude-stack).

## Архитектура сессии

Главная модель сессии (Fable 5.1) отвечает за три вещи: ставит задачу, выбирает исполнителя, ревьюит результат. Она не читает код файлами и не правит его сама — это текстовое правило в глобальных инструкциях.

**Почему без хука:** раньше правило держал хук `decider-gate` на `PreToolUse` для `Edit`/`Write`/`MultiEdit`/`NotebookEdit`; его сняли, потому что правки через Bash (heredoc, `sed -i`) он не ловил и реальные записи из главного потока проходили мимо.

### Матрица моделей по сложности

Субагентов запускают с моделью и уровнем effort, минимально достаточными для задачи — не «на всякий случай мощнее». Дефолт субагента — `opus` (Claude Opus 5.5, `CLAUDE_CODE_SUBAGENT_MODEL=opus`), effort `medium`: на medium Opus 5.5 держит уровень Opus 5 на high примерно за половину токенов.

| Модель | Сложность | Примеры задач |
|---|---|---|
| haiku | Механика/read-only | Explore, поиск файлов, чтение конфигов, grep, запуск готовых команд — не код |
| opus, effort medium | Основная работа | Написание кода, фиксы багов, рефакторинг, тесты, IaC, диагностика, планирование |
| opus, effort high | Сложные | Ревью кода, аудит безопасности, архитектура, консультант эскалации |
| sonnet | Фоллбек | Горящий недельный лимит, массовый boilerplate (или внешний воркер `qwen`) |

Правила выбора: по умолчанию — opus на effort medium; haiku — только read-only механика, не код; effort high — ревью, security audit, архитектура и second opinion; сначала снижай effort, потом меняй модель, sonnet — только фоллбек; Explore-агент всегда на haiku (он для быстрого поиска); Plan-агент — opus, effort high (качество планирования критично для последующих фаз). Самый тяжёлый хвост задач по-прежнему за Fable, но только по явному разрешению (`fable-deep`).

Матрица не бралась с потолка — периодически проверяется replay-эвалом на реальных смёрженных PR (4 приватных репозитория, 2 стека). Методология: репозиторий клонируется через `git clone --no-local`, в клоне срезаются все ветки, теги и reflog до состояния «перед PR» — агент не должен видеть будущий мёрдж через `git log --all`. Ранняя версия эвала на worktree вместо изолированного клона этой защиты не имела: агент подсматривал будущий коммит через `git log --all` и копировал его побайтово, из-за чего jaccard 1.0 получался «из воздуха», а не из реальной работы модели.

Итог 117 прогонов:

| Модель | n | mean jaccard | пустых диффов | jaccard ≥ 0.8 | cost | duration |
|---|---|---|---|---|---|---|
| haiku | 38 | 0.21 | 61% | 11% | $0.24 | 173с |
| sonnet | 38 | 0.49 | 8% | 24% | $0.91 | 457с |
| opus | 38 | 0.60 | 3% | 32% | $1.86 | 401с |
| fable | 3 (проба) | — | — | — | — | — |

Устойчивость по репозиториям (mean jaccard haiku/sonnet/opus): 0.18/0.54/0.54, 0.25/0.45/0.57, 0.14/0.50/0.66, 0.26/0.50/0.63 — разброс между репозиториями заметный, но порядок моделей (opus ≥ sonnet ≫ haiku) стабилен на каждом из четырёх.

Fable-проба (n=3, вывод предварительный — выборка слишком мала для полноценного места в матрице): паритет с sonnet на 2 задачах из 3; на одной MR fable дал jaccard 1.00 за $0.87/48с там, где sonnet сдался (jaccard 0.00), а opus взял её за $2.12/305с с jaccard 0.42.

Выводы: haiku снят из маршрутизации кода целиком — 61% пустых диффов означает, что модель в большинстве случаев не вносит изменений вообще, а не вносит их плохо. Sonnet остаётся дефолтом для кода, opus — при затыке sonnet или на критичном коде (вывод эксперимента августа; с выходом Opus 5.5 дефолт субагентов — opus на effort medium, см. матрицу выше). MR больше ~30 изменённых файлов уверенно не решает ни одна модель (диапазон mean jaccard 0.11–0.52 по всем трём) — это сигнал декомпозировать задачу, а не менять тир модели. Даже лучшая модель в выборке доводит до jaccard ≥ 0.8 только около трети задач.

Ограничения методологии, честно: скоринг v1 — jaccard по набору изменённых файлов плюс объём диффа, без семантического сравнения содержимого. Прогон тестов на replay-патче не делался — эвал проверяет, что патч похож по форме на человеческий, а не что он рабочий. Оба пункта — кандидаты на v2, а не скрытые допущения.

Сам инструмент — `scripts/golden-pr-replay.py`, три подкоманды: `list --repo /path/to/repo` (нетривиальные merge-коммиты репозитория с долей lockfile/generated строк), `run <merge_sha> --model haiku|sonnet|opus|fable --repo /path/to/repo` (один replay с контаминационной защитой и записью метрик в `results/`), `report` (сводная таблица по всем прогонам).

### Эскалация вместо угадывания

Дешёвый агент, упёршийся в критичную развилку, не обязан гадать или молча эскалировать себя до дорогой модели. Два пути:

- **`consult-opus.sh`** — headless second opinion: read-only вызов Claude в print-режиме (`claude -p --model opus --effort high --max-turns 6 --allowedTools "Read,Grep,Glob"`), лимит 6 ходов, модель и effort переопределяются переменными окружения (`CONSULT_MODEL`, `CONSULT_EFFORT`). Возвращает вердикт одной строкой + обоснование в 2-5 предложениях + на что обратить внимание.
- **`ESCALATE: <вопрос>`** в отчёте субагента — main решает сам или адресует точечный вопрос opus-агенту на effort high. Эскалируется вопрос, а не вся задача — не нужно перезапускать работу целиком на дорогой модели.

Лимит — 1-2 эскалации на задачу.

### Внешние дешёвые воркеры (OpenRouter)

Рутинные атомарные задачи (саммари, парсинг, конвертации, boilerplate, кодовые правки по точному брифу) можно вынести за пределы подписки на внешние модели через OpenRouter — это дешевле любого тира Claude на порядок.

`or-task.sh [-m flash|pro|qwen] [-o max_tokens] [-t timeout_s] "бриф" [файл ...]`

| Алиас | Класс модели | Для чего |
|---|---|---|
| `flash` (дефолт) | компактная модель общего назначения | саммари, парсинг, конвертации, boilerplate, черновики |
| `pro` | модель среднего класса | тяжёлые черновики и планы |
| `qwen` | code-специализированная модель | кодовые правки по точному брифу — самая буквальная из трёх |

Встроенные ограничители: cap на `max_tokens` (по умолчанию 4096), таймаут на весь вызов (по умолчанию 180 с), cap на объём входа (~300k символов — больше делить задачу, не заливать целиком). Ключ читается из локального env-файла, никогда не коммитится.

Фоллбэки — тихая замена исполнителя запрещена, всё проговаривается в чате:
1. Сбой API → один ретрай → sonnet-субагент с явной пометкой, что сработал фоллбэк.
2. Провал качества → один ре-бриф той же модели → эскалация на opus; не больше одного круга.
3. Аномальная цена вызова (вышла за ожидаемые cap'ы) → стоп и отчёт пользователю, а не тихое продолжение.
4. Ключ невалиден или баланс исчерпан → явное сообщение, дальше работа на подписке с пометкой в сессии.
5. Автоматического отката вниз по качеству нет — понижение тира только осознанным решением на новой задаче.

Результат внешнего воркера всегда ревьюит main сам (diff или вывод читает, а не верит отчёту) — скоупинг чужой работы дороже самой экономии, если его пропустить.

## PM-конвейер

Скилл `pm` — оркестрация нетривиальных задач: main не делает работу сам, а решает, распределяет по субагентам и сводит результат. Работает как для кода, так и для не-кодовых продуктовых задач.

### Phase 0 — Classify

Три вопроса без запуска агентов:

1. **Greenfield или brownfield?** С нуля → сначала выбор паттерна (Phase 0a); правка существующего → сначала research конвенций (Phase 1).
2. **Размер задачи:**

   | Size | Триггер | Воркеры | Роль main |
   |---|---|---|---|
   | S | <50 строк / 1-2 файла / понятный фикс | 1× opus (medium) | супервизия + ревью |
   | M (дефолт) | 50-500 строк, 1 модуль | 2-3× opus (medium) | план + сведение |
   | L | 500+ строк, много модулей | 4-6 разных моделей | полный конвейер |
   | XL | архитектура / больше пары дней / auth-payments-данные | 6-10 разных моделей, effort max | полный конвейер + аудит безопасности |

3. **Меняешь общий интерфейс?** (адрес, host, порт, DNS, схема БД, контракт API, формат сообщения). Если да — задача превращается из «поднять артефакт» в «не сломать потребителей»: обязателен инвентарь потребителей ДО переключения и проверка со стороны каждого потребителя ПОСЛЕ, а критерий готовности строится из потребителей, а не из самого артефакта.

Когда `/pm` не нужен: 1-2-строчная правка в файле, который уже открыт; прямой ответ на вопрос; чистая документация или опечатка — если main сделает быстрее сам, чем брифовать агента, не оркеструет.

### Чек-лист смены общего интерфейса

Пять шагов, если ответ на вопрос 3 — «да»:

- **Инвентарь потребителей** — кто зовёт интерфейс, с какого хоста/сети, каким путём, чем и откуда аутентифицируется. Грепается весь доступный контекст (скиллы, env контейнеров, репозитории, DNS), не только текущий репозиторий.
- **Критерий готовности из потребителей** — по строке на каждого потребителя + хост, откуда он проверяется. «Артефакт отвечает мне» критерием не считается.
- **Топология как вход плана** — NAT/hairpin/firewall решаются для каждого пути потребителя до переключения, не после.
- **Cutover** — механика переключения; для stateful-систем — заморозка записи → финальный дамп → переключение → проверка данных.
- **Проверка из каждого потребителя** его реальным путём (адрес + источник креда). Задача считается закрытой только когда все потребители прошли проверку из своих точек, не из точки оператора.

### Phase 0a — выбор паттерна (только greenfield)

Для задачи с нуля, без референса в текущем репозитории, один агент-архитектор (opus, effort high) предлагает 2-3 паттерна реализации в формате «паттерн | плюсы | минусы | для чего лучше подходит | риск» и финальную рекомендацию. Очевидный выбор фиксируется в `plan.md` под отдельным разделом; близкие по весу варианты выносятся на явный выбор пользователя, а не решаются молча. Дальше конвейер не идёт без зафиксированного паттерна — это самая дешёвая точка для смены архитектурного решения, дальше цена ошибки растёт.

### Research → Plan → Worker resolution

- **Research (brownfield, параллельно):** Explore на haiku — существующие конвенции; аналитик на opus (medium) — доменная экспертиза, если нужна; blast-radius-агент на opus (medium) — обязателен при смене интерфейса. Конвенция проекта весит больше общих best practices; если конвенции нет — эскалация на выбор паттерна.
- **Plan (main):** `plan.md` с разделами Goal / Non-goals / Assumptions / Success criteria / Pattern / Steps (каждый шаг — с `verify:`, командой или тестом, а не словом «работает») / Risks / Outcome. Пути в шагах — точные (`file:line`, где известно), чтобы следующая сессия могла продолжить без повторного ресёрча.
- **Регистрация в `_active.md`** — построчный индекс активных задач (`slug | status | next action | дата обновления`), который автоматически подтягивается в каждую новую сессию через `SessionStart`-хук. Одна строка — одна сессия-владелец; чужой slug не перехватывается.
- **Worker resolution** — сначала смотрим на существующий флот агентов, домен подходит частично — используем и добавляем специфику в бриф. Домен повторяемый и специалиста нет — заводим нового агента (frontmatter: `name`, конкретные trigger-фразы в `description` — от них зависит авто-делегация, `tools` по минимуму, модель по матрице). Одноразовый домен — обычный `general-purpose` с подробным брифом, агента не плодим.

### TDD-цикл

Обязателен для: фиксов багов (тест, воспроизводящий именно сценарий из репорта, пишется до фикса), контрактов API, бизнес-логики, критичного кода. Пропускается для UI-правок, конфигов, чистого рефакторинга при существующих тестах, спайков, документации.

Цикл: **Red** (агент-автор теста подтверждает, что тест падает) → main читает диф теста (нет ли подгонки под ответ, пустых assertion'ов) → **Green** (агент-разработчик доводит до зелёного минимальными правками) → опционально **Refactor**.

Каждый бриф разработчику включает обязательный блок «Правила кода»: минимум кода без фич сверх брифа; трогать только заявленные файлы, не улучшать соседнее; каждая изменённая строка должна прямо следовать из брифа; критерий успеха прогоняется перед отчётом, вывод прикладывается. Без этого блока в брифе агент по умолчанию «улучшит» половину файла заодно.

### Verify — из точки потребителя, не оператора

Ключевое правило фазы верификации: собственная машина — почти всегда точка с гарантированно рабочим внешним путём, поэтому проверка с неё даёт **ложный зелёный** (классическая ловушка: запрос снаружи отвечает 200, а потребитель во внутренней сети лежит). Каждый потребитель проверяется с его собственного хоста и его собственного реального пути аутентификации — подстановка своего или пустого креда вместо того, что реально использует потребитель, даёт **ложный FAIL** (401/403 на рабочем сервисе). При «connection refused» от потребителя сначала проверяется, слушает ли сервис на его реальном адресе — в большинстве случаев дело в адресе или маршруте, а не в самом сервисе.

Verify возвращает вердикт `PASS/FAIL/WARN` с issues, размеченными по severity, где каждый issue мапится на конкретную непройденную букву CLEAR. FAIL уводит обратно в фазу разработки с точным диффом и списком issues; WARN — на обсуждение; PASS — в фазу сведения.

### Модели по ролям в конвейере

| Роль | Модель |
|---|---|
| PM (main) | Fable 5.1, effort high |
| Research / аналитик / разработчик / тестировщик / `git-workflow-manager` | opus (Opus 5.5), effort medium |
| Архитектор / `code-reviewer` / `security-auditor` / критичное ревью / планировщик | opus (Opus 5.5), effort high |
| Explore / точечный lookup / механика (поиск, чтение, запуск команд) | haiku |
| Boilerplate по точному брифу | внешний воркер `qwen` |
| Фоллбек при горящем недельном лимите | sonnet |

Сначала снижай effort, потом меняй модель; sonnet — только фоллбек. Дорогой уровень (effort high, Fable) — это выбор для конкретной развилки, а не тир по умолчанию.

### Reconcile и hard caps

Main читает артефакты задачи, заполняет `Outcome` в `plan.md` (что сделано, что нет и почему, какие решения принял пользователь), закрывает или обновляет строку в `_active.md`, предлагает `/clear`. Планы не удаляются — это журнал аудита.

Жёсткие ограничения конвейера: не больше 3 параллельных research-агентов; 1 dev-агент на файл; не больше 10 параллельных агентов в одной волне; крупные артефакты уходят в файлы задачи, в чат — только ссылка и короткое summary.

### Частые провалы конвейера

Список составлен по фактическим повторяющимся ошибкам, а не гипотетически:

- Бриф разработчику без блока «Правила кода» — воркер честно перепишет полфайла «для красоты», потому что явного запрета не было.
- Шаг плана без `verify:` — «сделано» без доказательства, которое можно перепроверить.
- Оркестрация запускается рефлекторно на задаче в 1-2 правки — там, где main справится быстрее сам.
- Дорогая модель — на grep или на печать 200 строк, которые main мог написать сам за то же время.
- Фабрика агентов — под одноразовую задачу, вместо `general-purpose` с подробным брифом.
- Расплывчатый `description` у нового агента («помогает с кодом») — авто-делегация не сработает, триггер-фразы должны быть конкретными.
- Верификация из точки оператора, где путь всегда рабочий, вместо точки реального потребителя — даёт ложный зелёный.
- Смена общего адреса, host или контракта без инвентаря потребителей — артефакт поднят, потребители лежат. Ровно этот класс провала выглядит как «перенесли, но не проверили».

## Принципы

### Karpathy guidelines

Четыре поведенческих правила против типичных ошибок LLM при написании кода:

1. **Think Before Coding** — не угадывать. Допущения проговариваются явно; если возможно несколько трактовок задачи — они показываются, а не выбираются молча; если есть путь проще — об этом говорится вслух; неясность — повод остановиться и спросить, а не продолжать.
2. **Simplicity First** — минимум кода, решающего задачу. Без фич сверх запрошенного, без абстракций ради одноразового кода, без «гибкости про запас», без обработки невозможных сценариев. Написал 200 строк, а могло быть 50 — переписать.
3. **Surgical Changes** — трогать только то, что нужно. Не «улучшать» соседний код, комментарии или форматирование по пути, не рефакторить рабочее, сохранять существующий стиль. Чужой мёртвый код — упомянуть, не удалять.
4. **Goal-Driven Execution** — определить проверяемый критерий успеха до реализации и крутить цикл до его выполнения. «Исправь баг» превращается в «напиши тест, воспроизводящий баг, затем сделай его зелёным».

### CLEAR — самопроверка результата

Перед тем как выдать нетривиальный результат — код, план, ресёрч, фактическое утверждение — он молча прогоняется по пяти буквам. Пункт не проходит — чинится; пункт нельзя проверить — это помечается явно, а не выдаётся как факт.

- **C — Correct.** Факты верны: числа, имена, пути, флаги, API действительно существуют — проверено в коде или командой, не по памяти.
- **L — Logical.** Внутренне непротиворечиво, вывод следует из посылок, без скрытых скачков.
- **E — Evidence-based.** Подкреплено источником — файл со строкой, вывод команды, документация — а не догадкой.
- **A — Aligned.** Отвечает именно на запрос, в рамках заявленного объёма, без отсебятины и недоделок.
- **R — Reproducible.** Одни и те же входы дают один и тот же результат, шаги повторяемы.

Karpathy-правила задают критерий до работы, CLEAR проверяет результат после — они дополняют друг друга, а не дублируют.

### Терсе-режим (caveman)

ALWAYS-ON: режет преамбулы, пересказ вопроса, вежливые концовки и hedging, оставляя код, команды, пути, конфиги, ошибки и числа байт-в-байт. Не применяется к текстам, которые явно попросили развёрнуто, и к текстам для внешних адресатов (commit message, PR description, письма) — там обычный стиль. Выключается на сессию словами «caveman off» / «verbose».

### stop-slop — вычистка AI-следов

Прогоняется через любой текст перед тем, как он уйдёт наружу — в тикет-трекер, рабочие чаты, коммиты, PR, командную документацию. Вычищает: прямые упоминания AI/модели/ассистента; мета-ссылки на внутреннюю кухню ресёрча; характерные буззворды (delve, leverage, comprehensive, robust, seamless, streamline, consolidate, modernize, enhanced, utilize, facilitate, ensure, foster, unlock, empower — и их русские аналоги вроде «обеспечивает бесшовную интеграцию»); обращение к себе в третьем лице; сводочный тон («вот краткая сводка», «в заключение»); оверэксплейн там, где хватит строки; симметричные списки-ради-списков и эмодзи-заголовки. На выходе — только чистый текст, готовый к отправке.

Отдельное жёсткое правило, действующее всегда и без исключений: никаких упоминаний AI/Claude/GPT/нейросетей в коммитах, PR, комментариях к коду и `Co-Authored-By`. Весь код и все коммиты должны выглядеть как обычная работа разработчика.

## TDD-governor (Probity)

[Probity](https://github.com/nizos/probity) — принуждение TDD через `PreToolUse`-хук с LLM-судьёй, который читает транскрипт сессии и решает, не пропущена ли Red-фаза. Преемник [tdd-guard](https://github.com/nizos/tdd-guard) от того же автора: tdd-guard переведён в maintenance mode, дальнейшая разработка идёт в Probity.

Почему замена, а не апдейт: tdd-guard требовал per-language тест-репортеры — источник собственных багов (гонки записи в `test.json`, ложные «passed» от рассинхрона репортера и реального прогона). Probity читает транскрипт вместо репортеров и одинаково работает с несколькими агентами (Claude Code, Codex, Copilot CLI), а не только с Claude Code.

Паттерн подключения:

```bash
npm install -D @nizos/probity
```

`probity.config.ts` в корне проекта:

```ts
import { defineConfig, enforceTdd } from '@nizos/probity'

export default defineConfig({
  rules: [
    { files: ['src/**', '!**/tests/**'], rules: [enforceTdd()] },
  ],
})
```

Project-level `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|Write|Edit|NotebookEdit",
        "hooks": [{ "type": "command", "command": "npx @nizos/probity --agent claude-code" }]
      }
    ]
  }
}
```

Честная оговорка о цене: судья гоняет пару моделей (быструю + сильную) на каждую in-scope правку через подписку — это не бесплатно при интенсивном кодинге. Ставить только туда, где тесты реально бегут локально, а не как декорацию; через 2 недели пилота сверяться с телеметрией расхода, а не с ощущением.

Статус на конец августа 2026: пилот в нескольких приватных репозиториях с 2026-08-30, имена не публикуются.

## Semantic search стек

Семантический поиск по коду — MCP-сервер `claude-context` поверх локального Milvus (векторная БД в Docker) и Ollama с моделью `qwen3-embedding:0.6b`. Полностью локально, без внешнего API — стоимость поиска нулевая. Индекс персистентный и обновляется инкрементально; при первой работе над проектом кодовая база индексируется один раз, дальше поиск идёт по готовому индексу.

Правило разделения инструментов: точный текст или известное имя символа — обычный `grep`/аналог с regex; поиск по смыслу («где у нас обрабатывается retry-логика для внешних вызовов») — semantic search.

Вторичный инструмент — CLI с построением графа вызовов (`trace`: кто вызывает функцию и что вызывает она), полезен для трассировки зависимостей, которые векторный поиск не покажет напрямую. Его фоновый демон-наблюдатель несколько раз умирал молча, поэтому теперь весь стек держится под сторожем: `scripts/semantic-stack-watch.sh` раз в 10 минут проверяет Milvus и демон и орёт при изменении состояния, разовая проверка — `scripts/semantic-stack-check.sh`.

### Установка

Эмбеддер локально, через Ollama:

```bash
ollama pull qwen3-embedding:0.6b
brew services start ollama            # или ollama serve
```

Milvus в Docker — standalone с встроенным etcd, конфиг и данные в `~/milvus-local`:

```bash
mkdir -p ~/milvus-local/volumes/milvus
cat > ~/milvus-local/embedEtcd.yaml <<'EOF'
listen-client-urls: http://0.0.0.0:2379
advertise-client-urls: http://0.0.0.0:2379
quota-backend-bytes: 4294967296
heartbeat-interval: 100
election-timeout: 1000
snapshot-count: 10000
EOF
echo '# Extra config to override default milvus.yaml' > ~/milvus-local/user.yaml

docker run -d --name milvus-standalone \
  -e ETCD_USE_EMBED=true -e ETCD_DATA_DIR=/var/lib/milvus/etcd \
  -e ETCD_CONFIG_PATH=/milvus/configs/embedEtcd.yaml \
  -e COMMON_STORAGETYPE=local -e DEPLOY_MODE=STANDALONE \
  -v ~/milvus-local/embedEtcd.yaml:/milvus/configs/embedEtcd.yaml \
  -v ~/milvus-local/user.yaml:/milvus/configs/user.yaml \
  -v ~/milvus-local/volumes/milvus:/var/lib/milvus \
  -p 19530:19530 -p 2379:2379 -p 9091:9091 \
  --restart unless-stopped \
  --health-cmd="curl -f http://localhost:9091/healthz" \
  --health-interval=30s --health-start-period=90s --health-timeout=20s --health-retries=3 \
  milvusdb/milvus:v2.6.20 milvus run standalone
```

Только стабильные теги `v2.6.x` — beta-ветка 3.0 крашлупится (проверено в июле 2026).

MCP-сервер в `~/.claude.json`, секция `mcpServers`:

```json
"claude-context": {
  "type": "stdio",
  "command": "npx",
  "args": ["-y", "@zilliz/claude-context-mcp@0.1.15"],
  "env": {
    "EMBEDDING_PROVIDER": "Ollama",
    "EMBEDDING_MODEL": "qwen3-embedding:0.6b",
    "EMBEDDING_DIMENSION": "1024",
    "OLLAMA_HOST": "http://127.0.0.1:11434",
    "MILVUS_ADDRESS": "127.0.0.1:19530",
    "MILVUS_TOKEN": "local"
  }
}
```

Размерность вектора зашита в коллекцию Milvus: сменить модель эмбеддингов можно только вместе с полным реиндексом, поэтому удобный момент для смены — когда коллекций ноль. Выбор `qwen3-embedding:0.6b` (1024 измерения, 110 мс на чанк кода в 3000 символов на M1 Max) — компромисс между `nomic-embed-text` (768, 42 мс, вдвое короче вектор) и `qwen3-embedding:4b` (2560, 542 мс — 13 часов на полный реиндекс).

Первая индексация проекта — инструментом `index_codebase` с абсолютным путём к корню, проверка — `get_indexing_status`. Индекс персистентный, дальше обновляется инкрементально. Батчем, без сессии Claude Code (например, после пересоздания Milvus, когда MCP-сервер подключается только на старте сессии), то же самое делает `scripts/reindex-claude-context.py`: он говорит с MCP-сервером по stdio и умеет `--status`, `--search`, `--clear`, `--force`.

Грабля, которая съедает вечер: Milvus уходит в крэш-луп с `panic: etcdserver: leader changed` сразу после `became leader`, exit 134, десятки рестартов. Причина не в «битом томе», а в гонке на старте: Milvus шлёт линеаризуемые чтения во встроенный etcd раньше, чем единственный узел выбрал себя лидером, получает `ErrLeaderChanged` и паникует. Окно гонки расширяется при увеличенных `heartbeat-interval`/`election-timeout` и под нагрузкой хоста — поэтому в конфиге выше стоят дефолты `100`/`1000`, а не «повышенные для надёжности» значения, которые ровно эту проблему и усугубляют. `snapshot-count: 10000` укорачивает реплей WAL на старте. Если луп всё же вернулся: `docker stop milvus-standalone`, дождаться падения нагрузки, `docker start`. Снос тома — последнее средство, а не первое: после него индексы пустые и всё надо переиндексировать.

Ещё две вещи, которые сбивают с толку при диагностике. Статус `Connected` у MCP-сервера ничего не доказывает — процесс поднимается независимо от базы и при мёртвом Milvus рапортует то же самое, а запросы уходят в никуда; проверять `curl -s http://127.0.0.1:9091/healthz`. И сессия, стартовавшая при мёртвом Milvus, инструментов поиска не получит вообще — после починки нужна новая сессия.

## Память (четыре слоя)

Каждый слой хранит свой тип информации, факт не дублируется между слоями — только ссылка.

| Слой | Что хранит | Кто пишет |
|---|---|---|
| `pm/<slug>/plan.md` + `_active.md` | Состояние задач: шаги, следующее действие, решения по конкретной задаче | PM-конвейер по ходу работы |
| Auto-memory (`MEMORY.md` + файлы) | Долгоживущие факты проекта: доступы, особенности, контракты, «как тут устроено» | Модель, когда факт переживёт задачу |
| Плагин памяти сессий | Хроника сессий для recall — пишется автоматически | Сам плагин, руками не трогается |
| `docs/` репозитория | Командное знание: гайды, разбор инцидентов, инвентарь | По правилам конкретного репозитория |

Правило записи: решение принято или факт установлен (где лежит доступ, от чего ломается сервис, что выбрали и почему) — строка уходит на диск в тот же ход, не «в конце сессии». Компактизация контекста может случиться в любой момент и ничего сама на диск не пишет.

Страховка на случай сжатия — два хука. `PreCompact` (`compact-state.sh`) снимает снапшот состояния в `~/.claude/compact-state/<session_id>.md`: TODO дословно, последние правленые файлы, факты окружения из успешных команд, ветка и worktree, путь `plan.md`, последние промпты; секреты вырезаются, права файла `0600`. Обратно в контекст снапшот возвращает `SessionStart` с `matcher: "compact"` (`postcompact-inject.sh`). Именно `SessionStart`, а не `PostCompact`: последний физически не может ничего доставить модели — его вывод идёт только в UI, поэтому привычный приём «в `PostCompact` сделать `cat` нужного файла» модель никогда не видит. Снапшот считается независимо от суммаризатора и переживает то, что тот решил выкинуть; но и после сжатия `plan.md` всё равно перечитывается, а не заменяется summary.

Факт, который уже есть в одном слое, в остальных живёт как ссылка, а не копия. Протух — чинится в источнике.

## Token economy

Метрики использования (запросы, токены, стоимость по сессиям и проектам) собираются через OTLP-телеметрию Claude Code в self-hosted Grafana — без передачи данных куда-либо ещё, инструмент личный.

Выводы из аудита, которые определили архитектуру сетапа:

- Порядка 75% недельных трат приходилось на главный поток — не на субагентов. Отсюда правило «main = decider»: главный поток не должен печатать код и читать файлы целиком.
- Суффикс `[1m]` в имени модели ничего не ограничивает: у старших моделей окно 1M нативное, функция выбора окна возвращает миллион ещё до проверки суффикса. Полгода «фиксов» ключа `model` не меняли ни средний контекст на ход (352k → 334k → 319k → 325k по неперекрывающимся неделям), ни цену. Единственный рабочий рычаг — `autoCompactWindow` в `settings.json` (или `CLAUDE_CODE_AUTO_COMPACT_WINDOW`): это порог срабатывания компакции, не размер окна после неё. Без него компакт у 1M-моделей включается в районе 967k, то есть практически никогда. Значение 200000 — в `settings.example.json`; побочка — в тяжёлых сессиях компакций становится в 5–10 раз больше, и если модель начинает забывать уже принятые решения, порог поднимается.
- Тяжёлый режим (`fable-deep`: 1M-контекст плюс максимальное усилие) вынесен в отдельного агента и запускается только по явному разрешению на конкретный вызов.
- Одна несброшенная сессия способна съесть двузначный процент недельного лимита за счёт постоянного перечитывания всего контекста на каждый ход (соотношение чтения кэша к выводу — на два-три порядка в пользу чтения). Отсюда дисциплина `/clear` на границе логических задач и ориентир: сессия перевалила за ~1500 запросов без смены типа работы — это уже не работа, а перечитывание истории.
- Statusline показывает темп расхода лимитов (5-часовое и недельное окно) прямо во время работы, чтобы не считать вручную.
- `promptCacheTtl` в `settings.json` (`5m`|`1h`) — TTL кэша промпта главной сессии. На подписке дефолт `1h`, но при уходе в overage тихо падает до `5m` — явный пин `1h` (см. `settings.example.json`) страхует от этого. `subagentPromptCacheTtl` — то же самое для всего, что не main; дефолт `5m`, поднимать до `1h` не рекомендуется — запись 1h-кэша дороже, а субагенты живут слишком коротко, чтобы это отбить. Требуется Claude Code ≥2.1.242; статистика кэша — в `/usage`, машиночитаемо — `usage.cache_creation` при `--output-format json`.

## Бэкап собственного сетапа

Отдельным паттерном, без прямой ссылки: приватный бэкап-репозиторий всего `~/.claude` с redaction-скриптами, вычищающими секреты и корп-контекст перед коммитом, и rolling-release веткой для тяжёлых бинарных данных (индексы, кэши). Такой репозиторий имеет смысл держать отдельно от публичного — он хранит личную конфигурацию целиком, а не только переиспользуемые куски.

## Как взять себе

1. Скопировать нужные директории (`skills/`, `agents/`, `hooks/`, `scripts/`) в `~/.claude/` — глобально, или в `<project>/.claude/` — под конкретный репозиторий.
2. Подключить хуки в `settings.json` — структура и матчеры показаны в `settings.example.json`; путь к скриптам поправить под свою систему.
3. Забрать общие принципы (Karpathy guidelines, CLEAR, правило «никаких следов AI», матрицу моделей) — шаблон в `CLAUDE.global.example.md`, дальше редактируется под свой стиль работы.
4. Проверить права на выполнение у скриптов (`chmod +x`) и наличие зависимостей, которые они вызывают (`git`, опционально `gitleaks` для сканирования секретов).
5. Заводить агентов и скиллы по мере необходимости, а не копировать весь флот сразу — специалист, который не используется, только шумит в контексте на старте сессии.
